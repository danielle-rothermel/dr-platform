# Platform and Whetstone implementation orchestration

Execute the frozen v6 Platform/Whetstone design as coordinated per-repository stacked PRs, with explicit state-machine matrices, final hard-cut deletion, cross-repo revision pins, automated review gates, Slack transition updates, and owner review only after the full verified constellation is complete.

## Review Surface

<Callout id="execution-decision" tone="decision">

This is an execution control artifact, not a new design gate. Implement the frozen v6 packet and ADRs 0022–0023 as final-intent code: fresh schemas, one runtime path, no dual reads or writes, no fallback adapters, no compatibility views, and deletion of replaced paths in the same stack that proves their replacements. Automated gates and agent review continue without owner pauses. Danielle reviews only the complete, cross-repo verified constellation.

</Callout>

### Outcome

Land coordinated Graphite stacks in `dr-platform`, `whetstone-ai`, and `unitbench` that replace the legacy enqueue, operational-analysis, and publisher paths with:

- a DBOS 2.26-backed Platform kernel with durable operations, attempts, claims, reconciliation, cancellation, inspection, and one public export verb;
- Whetstone Generation and Scoring Operations, populated-only selection, strict experiment acceptance, and atomic Analysis and Detail publication bundles;
- Unitbench two-plane reads through pinned Analysis and Detail adapters; and
- a reproducible constellation manifest proving the exact revisions, schemas, bundles, deployment, and end-to-end gates reviewed together.

The reviewed v6 packet remains frozen. Implementation matrices and evidence live outside it.

## Operating rules

1. Verify each repository's canonical `main` against its remote, then root a `v6-bootstrap` PR directly on that commit. Cherry-pick only the accepted planning/ADR commits into the bootstrap PR; the first implementation PR stacks on it. Existing planning branches are never used as hidden or permanent dependency bases.
2. Every PR begins with its state-machine/scenario matrix and focused failing tests. The implementation makes that matrix pass in the same PR.
3. Keep PRs draft while the stack is moving. Automated checks and fresh-agent review gate each PR; owner approval does not.
4. Open and update PRs with Graphite. A child PR never pins an unreviewed intermediate commit from a sibling repository.
5. Delete a legacy path only in the PR that proves the replacement end to end. Do not retain a shim “temporarily.”
6. Stop only on baseline drift, unexpected mutations, a failed feasibility preflight, or a genuine owner decision not settled by v6/ADRs. Otherwise repair and continue.
7. Post `#progress` at each transition: planning → implementation, each PR published, stack advance, cross-repo pin, integration gate, deployment gate, and completion. If input is required, post to both `#progress` and `#high-pri`.

## Phase 0 — deterministic bootstrap and feasibility

No production implementation slice begins until Phase 0 is green.

1. Fetch and record canonical `main` SHAs for all three repositories. Stop on drift or local mutation.
2. Create `platform/v6-bootstrap`, `whetstone/v6-bootstrap`, and `unitbench/v6-bootstrap` directly from those SHAs. Cherry-pick the accepted frozen packet, ADR, vocabulary, and execution-plan commits that belong in each repository; verify the resulting diffs contain documentation/control artifacts only.
3. Publish those bootstrap PRs as the stack roots. Their descendants may remain draft and unmerged until final owner review; “canonical base” means the root parent is canonical `main`, not an old planning branch.
4. Run one blocking cross-repo feasibility PR/commit series before P1:
   - installed DBOS 2.26 signatures, system schema, queue/priority, serialization, cancellation, and allowlisted telemetry reads;
   - Postgres advisory locks and fresh-schema ctype behavior;
   - local DuckDB OS locking and SQL parity;
   - tiny live MotherDuck Postgres Lease, conditional renewal, fencing, atomic pointer, and query compatibility;
   - tiny live Neon pooled transaction/fencing and Detail query proof;
   - Unitbench Node runtime, server-only `DATABASE_URL`/`ANALYSIS_DATABASE_URL`, independent missing-secret behavior, no native DuckDB in the Vercel bundle, and same-fixture local-versus-deployed query parity.
5. Record provider/project identifiers without secrets. Any infeasible contract blocks the entire production stack before P1.

## Required state-machine matrices

### Platform source barrier

| State | Event | Next | Invariant |
| --- | --- | --- | --- |
| open | writer begins | shared-held | Owning mutation function acquires shared transaction lock internally. |
| shared-held | mutate | shared-held | Trigger assigns monotonic `change_seq`. |
| shared-held | commit/rollback | open | Lock releases with transaction. |
| open/shared-held | exporter requests | draining | Exclusive session lock waits for existing writers. |
| draining | exclusive acquired | snapshot | Repeatable-read begins only after exclusive acquisition. |
| snapshot | capture/extract | released | Extract `previous < change_seq <= high_water`; record truthful coordinates. |
| snapshot | failure | released | Roll back source transaction; destination is unchanged. |
| released | publish destinations | open | No source lock is held during remote work. |

### Destination lease, fence, and promotion

| Current | Event | Outcome |
| --- | --- | --- |
| absent/idle | acquire | Create/increment fence token, set owner and expiry. |
| same live owner | renew | Extend only through owner/token/unexpired CAS. |
| other live owner | acquire | Typed `LEASE_HELD`; no blind retry. |
| leased | stage/member failure | Prior pointer/cursors remain; owned stages are recoverable. |
| leased | renewal CAS lost | Abort before validation/promotion. |
| validated | newer snapshot | Atomically promote all members, cursors, checksums; clear lease. |
| validated | equal snapshot/equal checksum | Idempotent success. |
| validated | older or equal/unequal | Typed stale promotion; current version untouched. |
| promoting | process death | Destination transaction commits state and data together or rolls both back. |

### Cross-source compatibility

P0 pins this contract before P1 begins:

- application coordinate: the captured application `snapshot_seq` plus `application_captured_at`, a UTC database-server timestamp read inside the barriered repeatable-read transaction;
- DBOS coordinate: the exact installed DBOS system-database snapshot identity available from its transaction plus `dbos_captured_at`, a UTC DBOS-database-server timestamp read in the telemetry snapshot transaction;
- comparison: `absolute(dbos_captured_at - application_captured_at)` in integer milliseconds; sequence/transaction coordinates are persisted for diagnosis but never compared across source families;
- configured bound: `max_capture_skew_ms`, immutable for an export configuration and repeated in every result; and
- failure: missing coordinates, timestamp reversal beyond clock-health tolerance, schema drift, or measured skew above the bound fails the combined compatibility result closed while preserving each bundle's independent transaction and the prior compatible pointer.

The numeric bound is derived once in P0 by a checked-in deterministic 100-run zero-work fixture on the actual sink topology: take the observed p99 absolute skew, add two measured scheduler quanta, round up to the next 100 ms, and cap at 5,000 ms. Record raw samples, clocks, formula, chosen integer, and environment. Exceeding the cap is a feasibility failure, not permission to widen it silently. A later bound change is a reviewed configuration-contract change.

| Application coordinate | DBOS coordinate | Measured relation | Outcome |
| --- | --- | --- | --- |
| present | present | skew ≤ `max_capture_skew_ms` and clocks healthy | Record both coordinates/timestamps, bound, and skew; compatible result may publish. |
| present | present | skew above bound | Fail closed; preserve prior compatible pointer. |
| present | missing/unreadable | unknown | Fail closed; never fabricate equality. |
| present | DBOS schema drift or unhealthy clocks | unknown | Retain previous DBOS projection and report typed failure. |
| equal-looking labels | independently captured | unproven | Never reuse or compare application `snapshot_seq` as a DBOS coordinate. |

### Pin and cleanup

| Pin state | Promotion | Cleanup | Reader behavior |
| --- | --- | --- | --- |
| active/unexpired | allowed | Retain pinned old bundle. | Continue exact bundle. |
| expired | allowed | May remove if neither current nor otherwise pinned. | Typed `PINNED_BUNDLE_GONE`. |
| missing, physical data present | allowed | Treat as unprotected. | Fail closed; never drift to latest. |
| active, member/checksum missing | allowed | Report integrity failure. | Typed pin/integrity loss. |
| COPRO sees typed loss | n/a | n/a | Abandon iteration results; restart from wait/export/new pin. |

### Whetstone selection and acceptance

| Output | Generation terminal state | Scoring Manifest membership | Strict acceptance | Explicit authorized override |
| --- | --- | --- | --- | --- |
| `null` | any | excluded | no | no |
| empty string | any | excluded | no | no |
| ASCII or declared non-ASCII whitespace only | any | excluded | no | no |
| populated | success | included | yes, if every other declared criterion passes | unnecessary |
| populated | PARTIAL | included | no | may select only with immutable operator-confirmed policy authorization and exact provenance |
| populated | failed/cancelled | excluded | no | no |

Selection is deterministic over the declared stable ordering and freezes all eligible runs, including plural runs for one Prediction. Acceptance derives its pinned winner separately. Partial populated output remains available for scoring evidence, never satisfies strict acceptance, and promotes only through the explicit persisted override path.

### Unitbench compute and store policy

| Plane/adapter | ALLOW | CONFIRM | LOCAL_ONLY | Missing configuration |
| --- | --- | --- | --- | --- |
| Analysis/local DuckDB | run locally | run locally | run locally | typed missing local Analysis store |
| Analysis/MotherDuck Postgres | run remotely | require explicit confirmation token | reject before query | typed missing remote Analysis store |
| Detail/Neon | declared Detail reads only | n/a | n/a | typed missing Detail store |

Analysis and Detail failures render independently. Neither plane falls back to the other.

## Gate strategy

### Per-PR gate

- matrix and focused tests committed before implementation;
- repo format, lint, type check, and focused tests;
- old-symbol/path search for the slice;
- fresh-agent findings-first review with every blocker/major and every contract-, schema-, safety-, or dependency-boundary finding resolved before the child PR begins. Only a minor, non-blocking finding whose correction cannot invalidate the current contract or downstream assumptions may carry forward, and it must name its owner PR and test;
- clean worktree and mutation audit before publishing/updating the PR.

### Stack gate

- full repository test suite on the stack top;
- fresh schema/store bootstrap from zero;
- deterministic crash injection at extraction, lease, renewal, each member stage, validation, promotion, and post-commit;
- deterministic stale-writer scenario A(H1), B(H2), B promotes, A rejected for every destination and `full_rebuild`;
- incremental/full kernel equivalence;
- static and dynamic proof that DBOS inputs, outputs, errors, roles, events, streams, and notifications are never selected or deserialized by export;
- no legacy imports, paths, runtime names, dependency declarations, or docs remain.

### Cross-repo constellation gate

1. Pin Whetstone to the reviewed P7 SHA and exact DBOS patch.
2. Pin publication manifests to the reviewed W8 SHA and record schema/bundle versions.
3. Create disposable Kernel, Analysis, and Detail stores from fresh schemas.
4. Run zero-spend Generation → populated selection → Scoring → acceptance → explicit export.
5. Hold an active COPRO pin while a newer promotion and cleanup run; prove exact-bundle continuity or typed restart.
6. Run Unitbench adapter parity across local DuckDB, MotherDuck Postgres, and Neon Detail.
7. Exercise every current Unitbench page and independent missing-Analysis/missing-Detail states.
8. Deploy a Vercel preview with Node runtime and server-only secrets; prove native DuckDB is absent.
9. Run full suites and old-name searches in all three exact revisions.
10. Write `constellation.json` with repository SHAs, lock hashes, DBOS version, schema IDs, queue/workflow names, bundle IDs/checksums, Vercel deployment ID, and evidence links.

Only after this gate passes is the complete constellation presented for Danielle's review and production switchover.

## Branch, PR, and notification protocol

- Use one Graphite stack per repository. Branch names match the PR identifiers above.
- Publish each PR as draft immediately after its per-PR gate; stack children remain based on their parent PR.
- Put the matrix/evidence path, exact commands, deletion list, and downstream dependency impact in every PR description.
- Post `#progress` when a PR is created, updated after review, or becomes the new stack top; include repo, PR/branch, gate result, and next slice.
- Do not request owner review on intermediate PRs. The final review entrypoint links the three stack tops, the constellation manifest, verification evidence, and a concise change/deletion map.
- Production switchover is a final-intent deployment: new environment variables and fresh stores become authoritative, old code paths are already absent, and rollback means redeploying the preserved old revision/config against the preserved old stores.
