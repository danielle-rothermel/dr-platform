Does dr-platform build deep modules?

Review of ~/drotherm/repos/dr-platform (≈16.5k source lines, 22 modules, 27 test files) against codebase-design/SKILL.md — deep modules, seams, ports, adapters, and the interface-is-the-test-surface rule. Single-use reference doc; all excerpts verified against commit 3820729.
Mostly yes — the engine rooms are deep and the seams are real, but the front door and the test suite don't match the philosophy.

The core modules (claims.py, submission.py, reconciliation.py, cancellation.py, PostgresPublicationFence) hide enormous behaviour behind a handful of functions, nearly every port has both a production and a test adapter, and every dependency category is handled the way the skill prescribes. The deviations are systematic rather than local: a 132-name flat package interface, three facades with very wide doors, a misplaced export↔publication seam, and a test suite that reaches past the interface it should be exercising.

§1The yardstick

The skill asks for deep modules — a lot of behaviour behind a small interface, placed at a clean seam, testable through that interface. The specific tests applied below:

Depth = leverage at the interfaceHow much behaviour a caller (or test) exercises per unit of interface learned. Not a line-count ratio.
The deletion testDelete the module: if complexity vanishes it was a pass-through; if it reappears across N callers it earned its keep.
The interface is the test surfaceCallers and tests cross the same seam. Testing past the interface means the module is the wrong shape.
Two adapters make a seam realOne adapter is a hypothetical seam — just indirection. A port needs production + test adapters to be justified.
Dependency categories drive the moveIn-process → merge. Local-substitutable → real stand-in, seam stays internal. Remote/external → port + injected adapter.
Accept dependencies, return resultsDon't construct collaborators inline; don't communicate through side effects.

§6Findings

Ordered by how much they undermine the skill's goals — leverage for callers, locality for maintainers, testability through the interface.

F1The package root is a 132-name flat namespace — a shallow front door on deep rooms HIGH

The README promises a five-step flow (register → submit → reconcile/wait → inspect → cancel), which needs perhaps 15–20 names. __init__.py exports 132, dominated by publication (26), backoff (14), and export (14). Depth is a property of the interface — and the package-level interface is nearly as wide as the sum of its parts, so the leverage the deep cores earn is spent at the door.

The same door is also incomplete: submit() accepts QueueLookup, PhysicalEnqueueAdapter, WorkflowObserver, and LifecycleObservationReader parameters, yet none of those types are exported at the root — a caller who wants to inject must reach into dr_platform.enqueue_runtime and dr_platform.reconciliation_runtime. The root is simultaneously too wide and too narrow.

Deepening move: curate the root to the README's flow (the verbs plus their option/result types and the ports the verbs accept); leave the rest importable from submodules. The vocabulary contract test already guards __all__, so shrinking it is a mechanical, test-enforced refactor.

F2Tests cross below the interface, pervasively HIGH

“The interface is the test surface” is the skill's sharpest rule, and it is the one this repo breaks most. Submodule imports outnumber root-package imports roughly 5:1; there are ~143 monkeypatch/patch( uses, many swapping module-level functions of the module under test; and an estimated 60–70% of DB assertions query the kernel's private tables directly rather than using the exported readers (inspect_operation, list_attempts, health_report) that exist precisely to be that seam. One test imports a private exception class outright:

tests/test_publication.py:46 · tests/test_claims.py:451–462
from dr_platform.publication import _StalePromotionError

# ...and the dominant assertion pattern across the suite:
with pg_engine.connect() as connection:
    attempt_row = (
        connection.execute(select(schema.item_attempts)).mappings().one()
    )
    claim_row = (
        connection.execute(select(schema.enqueue_claims)).mappings().one()
    )
assert attempt_row["enqueue_state"] == "enqueued"
assert claim_row["disposition"] == "outcome_recorded"

Two caveats keep this from being worse than it looks: asserting on the export destination's tables is legitimate (that output is the product), and the DBOS fakes assert behaviour at a real seam. But per the skill, tests that must change when internals change are testing past the interface — and most of these would.

Deepening move: migrate internal-table asserts to the inspection readers; where a fact is unreachable through any reader, treat that as an interface gap in inspection.py rather than a reason to query the table. Then apply “replace, don't layer”: delete the absorbed low-level tests.

F3The export ↔ publication seam is drawn in the wrong place HIGH

publication.py is one deep class (PostgresPublicationFence, ~2,500 lines) surrounded by ~24 shallow models, signers, and free functions that all ride into the root namespace. Meanwhile export.py contains two near-duplicate ~180-line publish skeletons (_publish_kernel_remotes / _publish_application_remotes: same ensure_schema → acquire_lease → stage → promote → result shape), both reaching back into publication via # noqa: PLC0415 -- import cycle lazy imports. The destination seam itself is untyped:

src/dr_platform/export.py:1778–1782 — a Sequence[Any] seam collapsed at runtime
    for fence in destinations:
        if not isinstance(fence, PostgresPublicationFence):
            raise TypeError(
                "remote destinations must be PostgresPublicationFence"
            )

Physical layout also leaks across the seam: callers must construct RemoteBundleMember.table_name values that exactly match fence.stage_table_name(...) or prepare_stage rejects them — the fence's internal naming scheme is part of export's code. By the deletion test, the duplicated skeletons are complexity that would reappear in every caller; they belong inside the module.

Deepening move: define a named destination port (the methods the duplicated skeletons already duck-type on), move the publish skeleton behind it once, and make table naming an internal detail the fence resolves itself. The import cycle disappears with the seam redrawn.

F4submit() is a 15-parameter door, duplicated verbatim in submit_jsonl() MEDIUM

The behaviour behind it is genuinely deep, but the interface is not small — 8 of the 15 are optional injected collaborators, and jsonl.py re-declares nearly the whole list, so every widening happens twice. The noqa waiver acknowledges the shape:

src/dr_platform/submission.py:354–369
def submit(  # noqa: PLR0913 -- explicit public facade contract

    source: ManifestSource,

    enqueue_adapter: PhysicalEnqueueAdapter | None = None,
    workflow_observer: WorkflowObserver | None = None,
    reconciliation_reader: LifecycleObservationReader | None = None,

The repo already knows the fix — export() bundles its six collaborators into ExportReconciliationDependencies, a single frozen dataclass with its own invariant check. Applying the same shape here collapses the door to ~5 parameters and de-duplicates submit_jsonl for free.

Deepening move: a KernelRuntime-style dependencies object (engine, resolver, schema, injected ports) passed to submit / reconcile / cancel / export alike — one thing to learn, constructed once.

Deepening move: a builder or define_target(...) constructor that derives the declaration and digest from the supplied callables, so consistency is produced rather than checked.

The caller also supplies the stage callback — the fence's own staging step, externalized. Combined with the required call order (ensure_schema → acquire_lease → prepare_stage → promote), a large share of the fence's internal protocol is part of its interface.

Deepening move: make prepare_stage return a token that promote consumes, folding the mutually-dependent optionals and the stage callback into state the fence already owns.

F7A correctness-critical lock constant is shared across the submission ↔ claims seam MEDIUM

src/dr_platform/claims.py:32
from dr_platform.submission import EXPORT_BARRIER_ADVISORY_KEY

Both modules also carry near-identical private _acquire_export_writer_lock helpers. Advisory-lock correctness now depends on two modules independently agreeing on a key and an acquisition pattern — the opposite of locality: a change to the barrier protocol must be verified in two places (three counting export.py's reader side).

Deepening move: one internal module owns the barrier (key + acquire/release functions); submission, claims, and export call it. The invariant then lives where it can be fixed once.

The inner layer honors the ClaimTransitionStore port (which has two real adapters), but the three near-identical page facades construct the Postgres store inline and offer no way to substitute it — a two-adapter seam reduced to a single-adapter path at the level callers actually use. Importing the module also imports the DBOS SDK unconditionally.

Deepening move: either accept the store at the facades, or — since the three facades share their whole skeleton — collapse them into one parameterized page runner where the wiring lives once.

F9backoff.py is a wide flat bag — 14 root exports over 338 lines LOW

src/dr_platform/backoff.py:113–128 — representative one-statement wrappers
def throttle_delay_seconds(
    connection: Connection,
    *,
    throttle_key: str,
    now: datetime,
    schema: PlatformSchema,
) -> float:
    return delay_until_unblocked_seconds(
        load_throttle_backoff_state(
            connection, throttle_key=throttle_key, schema=schema
        ),
        now=now,
    )

No leaked privates — each export is a genuine operation on the throttle table, and the truly internal helpers stay internal. But the interface is nearly as large as the behaviour: callers must learn the throttle-key scheme and the block-vs-hold distinction across 12 functions, plus a redundant alias (ThrottleBackoffState = ThrottleState). A shallow module that is at least honestly scoped.

Deepening move: if callers typically compose these (record → compute → hold), a ThrottleGate with 3–4 methods would absorb the composition; otherwise, at minimum drop most of them from the package root (see F1).

The reconciliation split itself is a real seam — persistence core vs DBOS-SDK side, same quarantine intent as dbos_config.py, and public consumers touch only one side. §7What's working — patterns worth protecting

These are the places where the repo doesn't just comply with the skill but illustrates it. Several would make good excerpts for the skill doc.

Two-adapter discipline is the norm, not the exception 12 of 14 ports have production + hand-written test adapters — real seams by the skill's own rule. The fakes are small classes recording events, not mock-library constructs, so tests read as behaviour at the seam.
DBOS uncertainty reconciliation is depth done right DbosEnqueueAdapter._exception_outcome (enqueue_runtime.py:696) turns "enqueue threw" into an authoritative-status re-lookup with race classification — a page of hard-won distributed-systems knowledge callers never see.
The vendor quarantine is explicit and enforced by shape dbos_config.py declares itself the single home of dbos._private shims and injects its initializers; the reconciliation split isolates the SDK the same way. When DBOS breaks compatibility, the blast radius is one small module.
Invalid states are unconstructible records.py validators enforce cross-field durable invariants (retry provenance, enqueue/priority coupling, cancellation-origin coupling) at construction. The interface is field names; the implementation is hundreds of lines of invariant law.
cancellation_truth.py is the extraction pattern to copy Pure read-only predicates, four consumers, zero back-imports, not exported at the root. Exactly what F7 and F10's shared pieces should become.
The vocabulary contract test guards the interface itself test_platform_v6_vocabulary.py pins closed enums, frozen strict models, required exports, and — unusually — removed legacy exports that must stay gone. It is the one test that truly treats import dr_platform as the seam, and the lever that makes F1's cleanup safe.
Dangerous orderings are hidden behind facades cancel_operation commits durable intent before any physical DBOS cancel; reconcile sequences recovery → observe → persist → enqueue within a page budget. Callers get one verb; the load-bearing order stays internal.
Time and randomness never became test problems now is a required parameter or derived from the database; wait loops inject clock/sleeper; jitter is deterministic via sha256. Whole categories of seams other codebases need simply don't exist here.
CI closes the escape hatches A real postgres:16 service container, connectivity verified before the run, and check_skip_budget.py failing the build on any unbudgeted skip — including "zero tests ran." The local-substitutable strategy can't silently degrade.
No module-level mutable state, anywhere Every module-level binding across the kernel is an immutable constant. Combined with frozen models, locality of state is structural, not conventional.

§8Recommended moves, ranked by leverage

  1. Curate the root interface to the README's flow (F1). ~15–20 names: the verbs (submit, reconcile, wait_operation, inspect_*, cancel_operation, export, request_next_attempt), their option/result types, and the ports those verbs accept. Update the vocabulary contract test in the same change — it's the enforcement mechanism.
  2. Point the test suite at the interface (F2). Replace private-table asserts with the inspection readers; treat unreachable facts as gaps in inspection.py; delete absorbed tests per "replace, don't layer." This is the change that makes every future internal refactor cheap.
  3. Redraw the export ↔ publication seam (F3). Name the destination port the duplicated skeletons already duck-type on, move the publish skeleton behind it once, internalize stage_table_name. The import cycle and the isinstance guard both dissolve.
  4. Bundle the facade collaborators (F4, F8). One dependencies object in the style of ExportReconciliationDependencies, shared by submit / reconcile / cancel; accept the store at the enqueue page facades or merge them into one runner.
  5. Give the export barrier one owner (F7). A leaf module holding the advisory key and its acquire/release helpers, imported by submission, claims, and export.
  6. Smaller shape fixes as they're touched (F5, F6, F9, F10). A target builder that derives declarations; a stage token consumed by promote; a ThrottleGate if backoff calls actually compose; promote shared reconciliation pieces into a leaf module.
