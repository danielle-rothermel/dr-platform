## F1. A not-yet-enqueued Attempt can be physically enqueued after logical cancellation, because DBOS cancel of an absent workflow row is a silent no-op and claims are neither guarded nor invalidated by cancellation intent
- **Severity:** major
- **Class:** local-correction
- **Plan contract:** §1.5 cancellation ("A racer therefore either commits before the cancellation lock and appears in the exclusivity predicate, or waits and then fails closed on the committed cancellation guard; it cannot attach between the predicate and the DBOS call", v3/plan.md:583-587; missing-workflow enqueue split, v3/plan.md:723-746; enqueue state machine, v3/plan.md:750-763; `CANCELLED` finalization "an exclusive local reference is logically finalized", v3/plan.md:621-623); ADR 0005; ADR 0019; unified invariant 7.
- **Evidence:** Installed `cancel_workflows` is an UPDATE filtered by `workflow_uuid IN (...)` (`dbos/_sys_db.py:845-877`): for a workflow ID with no `workflow_status` row it matches zero rows, raises nothing, and creates no sticky `CANCELLED` tombstone. A later `enqueue_workflow` with that same ID then inserts a fresh `ENQUEUED` row that will dequeue and run (`dbos/_sys_db.py:670-704`). V3 makes this reachable on the mainline: Attempt rows carry their deterministic `workflow_id` from insert (v3/plan.md:281-292), so an Attempt in enqueue state `PENDING`/`CLAIMING` is a cancellation candidate before any DBOS row exists; the enqueue sequence persists the Claim, then calls DBOS outside any transaction, then records the outcome with a CAS on `(item_id, attempt, claim_id, enqueue_state)` (v3/plan.md:725-728). Cancellation changes only the execution column to `CANCEL_REQUESTED` (v3/plan.md:578-580, 771-772) — nothing invalidates an outstanding Claim or bumps `enqueue_state`, and the claim row `PENDING → CLAIMING` has no cancellation-intent predicate (v3/plan.md:752). The new-reference guard covers only "creating or linking a new reference" (v3/plan.md:581-583); a claim on an existing reference is neither. Walk the race: claimant wins its Claim CAS and commits; cancellation serializes after it on the Operation row, commits intent, calls `cancel_workflow` for the snapshotted ID — a silent no-op — and the final transaction finalizes the exclusive local reference sticky `CANCELLED` (v3/plan.md:621-623); the claimant's in-flight `DBOS.enqueue_workflow` then creates and starts the workflow. Its outcome CAS fails against the now-terminal immutable row (triggers, v3/plan.md:329-331), and the plan's only instruction for a lost CAS is "the loser reloads rather than applying its stale result" (v3/plan.md:745-746) — but the DBOS side effect has already happened and no compensation is specified. The same hole exists without any race: an Operation with `CANCEL_REQUESTED` Attempts still in enqueue state `PENDING` can be claimed and enqueued by a concurrent bounded reconcile pass, because claim eligibility nowhere excludes cancellation intent.
- **Consequence:** A paid generation/scoring workflow executes at DBOS while its only platform reference is terminal `CANCELLED` and the Operation reports `CANCELLED` — silent unaccounted spend invisible to reconciliation (terminal rows are immutable), inspection, health ("incomplete cancellation" never triggers: the cancellation accounted itself successful), export, and cost reconciliation. This is not the accepted ADR 0019 overlap (a continuing in-flight provider call inside an already-cancelled workflow); it is a whole workflow starting after cancellation claimed success, i.e. exactly the hidden/unaccounted overlap the owner decision does not cover. Alternatively, an implementer who waits for observed DBOS `CANCELLED` before finalizing leaves the Operation stuck `CANCELLING` forever for never-enqueued Attempts (no row will ever report `CANCELLED`). The quoted racer-exclusion sentence is false for the enqueue path on the installed dependency.
- **Required plan change:** Four bounded rules in §1.5: (1) claim eligibility requires no cancellation intent — an Attempt with execution state `CANCEL_REQUESTED` or terminal is never claimable; (2) the cancellation intent transaction invalidates outstanding enqueue Claims on affected Attempts (bump/clear `claim_id` or move `enqueue_state` to a terminal `ENQUEUE_CANCELLED` value) so any in-flight claimant's outcome CAS must fail; (3) a claimant whose outcome CAS fails against a cancellation-finalized Attempt must, before abandoning, issue the idempotent `cancel_workflow` for the workflow ID it just enqueued (the row now exists, so the cancel is effective) and record a typed compensation fact; (4) the final cancellation transaction distinguishes a `NOT_ENQUEUED` disposition (no DBOS row observed) from a delivered cancel, rather than recording a silent no-op as success. Add cancel-during-claim and cancel-then-late-enqueue to §4.3 and gate 4.

## F2. Two accepted `SUCCESS` Generation Runs for one Prediction are plan-sanctioned, but strict acceptance has no accepted-run selection rule, so the expected score matrix is ambiguous
- **Severity:** major
- **Class:** local-correction
- **Plan contract:** §2.4 strict acceptance ("every Manifest Prediction to have one accepted `GenerationRunStatus.SUCCESS` Generation Run and every required scoring profile for each accepted run", v3/plan.md:1323-1329); acceptance member matrix (v3/plan.md:1358-1366, 1371-1376); §1.5 ("The old Attempt remains terminal even if shared DBOS work later succeeds for another Operation", v3/plan.md:598-599; `OPERATOR_CANCEL_RETRY`, v3/plan.md:661); ADR 0018; ADR 0020; prompt requirement that "accepted domain outcomes are unambiguous."
- **Evidence:** Walk a plan-sanctioned sequence. Operations B and C of one experiment share content-scoped execution E at ordinal `n` (content identity is deliberate, ADR 0001; `prediction_id` hashes `experiment_name`, `whetstone-ai/src/whetstone/records/hashing.py:29-51`). B cancels; E is shared, so B's Attempt `n` finalizes sticky `CANCELLED` as skipped-shared (v3/plan.md:594-599, 772) while E keeps running for C. An operator confirms `OPERATOR_CANCEL_RETRY` for B — explicitly legal immediately after local `CANCELLED` (v3/plan.md:606-609, 661) — creating ordinal `n+1`, a new content identity, and Generation Run R2. E later completes and C persists Generation Run R1 (`generation_run_id` hashes Prediction ID, recipe digest, and `n`, v3/plan.md:1261-1263; the run row is a content-scoped domain row, not Operation-local). Both R1 and R2 can reach `GenerationRunStatus.SUCCESS` for the same Prediction. §2.4 defines acceptance per "each accepted run" but never defines which `SUCCESS` run is *accepted* when more than one exists; the member key includes `generation_run_id` (v3/plan.md:1358-1361), so the two readings produce different expected matrices — one implementation requires every required profile scored for both runs (doubling required scoring cells and cost), another selects the highest ordinal, a third selects any `SUCCESS` row. The evaluator "derives the full expected/observed matrix" (v3/plan.md:1372-1373) with no derivation rule for this case, and the scoring-selection freeze (v3/plan.md:1246-1254) inherits the same ambiguity when both runs are selection-eligible.
- **Consequence:** Two conforming implementations disagree on whether the same Experiment is `COMPLETE` or `PARTIAL`, and on which score cells are required — precisely the "Experiment that appears valid when it is not" class: an evaluator that picks R2 can report strict completeness while R1's required profiles were never scored, and vice versa. Because the scenario is produced by the operator cancel-retry path racing shared work — a path §1.5 explicitly preserves and gate 4 exercises — this is a mainline incident-recovery flow, not a contrived corner.
- **Required plan change:** State one accepted-run selection rule in §2.4/ADR 0018 — recommended: for each Prediction, the accepted Generation Run is the `SUCCESS` run with the highest platform Attempt ordinal at the evaluation's source cut (with the tie impossible by construction since ordinals are unique per Item), and earlier `SUCCESS` runs are recorded in members as superseded rather than expected. Require the scoring-selection derivation to apply the same rule so a frozen selection never demands cells for a superseded run, and add the shared-work-late-success-after-cancel-retry acceptance walk to §4.3 and gate 3.

## F3. The Whetstone Analysis Bundle's member inventory is enumerated inconsistently in three places
- **Severity:** minor
- **Class:** local-correction
- **Plan contract:** §1.6 client augmentation ("e.g. Whetstone's predictions/generation-runs/score-attempts projections", v3/plan.md:941-942); §2.4 ("registers its domain projections … predictions, generation runs, node attempts, score attempts", v3/plan.md:1289-1291); §4.1 ("the Whetstone full-rebuild projections `experiments`, `predictions`, `sweep_metrics`, and `failure_metrics`", v3/plan.md:1493-1494).
- **Evidence:** The three enumerations of the same atomic Analysis Bundle do not agree: §2.4 promises generation-run/node-attempt/score-attempt projections in the analytical plane, while §4.1 — the section that defines the bundle boundary, reader skew policy, and the Unitbench replacement mapping for `published_*` reads — lists a different four-member set and places node/score detail only in the Detail Store (v3/plan.md:1520-1533). COPRO's pinned Analysis reads (v3/plan.md:1402-1409) need per-candidate score results, which exist in one enumeration (`score_attempts`) and only as unspecified aggregates (`sweep_metrics`) in the other.
- **Consequence:** Bundle membership defines what promotes atomically and what readers may join without skew checks; two implementers building phase 7 from §2.4 versus §4.1 produce different bundles, different Unitbench table configs, and a COPRO adapter that may find no table carrying candidate-level scores. The atomic-pointer guarantee is only as meaningful as the agreed member list.
- **Required plan change:** Make one section (recommend §4.1) the authoritative Analysis Bundle member inventory, reconcile §1.6/§2.4 to reference it, and state explicitly which table COPRO's candidate-score reads use.

## F4. `ItemExecutionRecipe` ownership is unstated: the kernel contract enumerates domain nouns without saying whether the kernel models them or treats the recipe as caller-opaque
- **Severity:** minor
- **Class:** local-correction
- **Plan contract:** §1.5 ("Each concrete `ItemExecutionRecipe` contains that Item's complete domain input snapshot; … and every relevant profile, parser, dataset, graph, provider-configuration, and application version", v3/plan.md:503-512); design principle 2 ("dr-platform … knows nothing about LMs, prompts, or scoring", v3/plan.md:23-26); dr-platform `CONTEXT.md` Execution Recipe entry.
- **Evidence:** The recipe is supplied through the kernel's `EnqueueTarget` and its digest is persisted on kernel Attempt rows and hashed into content-scoped workflow identity (v3/plan.md:505-512), but the plan never states whether `ItemExecutionRecipe` is a kernel Pydantic model with the enumerated fields (which would put profile/parser/dataset/graph/provider-configuration vocabulary into the domain-agnostic kernel, violating principle 2 and the vocabulary rule) or a caller-owned frozen model whose canonical-JSON payload the kernel treats as opaque and only digests. The §1.8 export inventory lists no recipe model either way (v3/plan.md:1167-1190).
- **Consequence:** Two conforming implementations diverge on the kernel's public surface and on where recipe validation lives; the kernel-model reading quietly breaks the domain-agnostic principle that the rest of the plan enforces, and golden digest fixtures (v3/plan.md:1257) cannot be pinned until the owning side is fixed.
- **Required plan change:** One sentence in §1.5: the kernel defines only a minimal frozen envelope (recipe version + canonical payload + derived digest, plus the kernel-required workflow name/topology/argument-recipe-version facts); the payload's domain contents are caller-owned and opaque to dr-platform, and Whetstone's concrete recipe model lives in whetstone-ai.
