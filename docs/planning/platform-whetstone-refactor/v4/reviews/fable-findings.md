## F1. The acceptance schema can represent only one generation Manifest per Experiment while the accepted-relationship table and Operation-key scheme permit several, leaving Experiment growth unrepresentable

- **Severity:** major
- **Class:** owner-decision
- **Plan contract:** `contracts/whetstone.md` § "Experiment-acceptance schema and transaction" (evaluation row: "the full SHA-256 digest of canonical `{…, generation_manifest_digest, scoring_manifest_digests, …}`"; "It persists status, the exact generation Manifest digest, a canonically sorted non-empty set of scoring Operation/Manifest digests") versus the same section's `experiment_operation_manifests` keyed by `(experiment_name, workflow_role, operation_key, manifest_digest)`; ADR 0020 ("Pin exact generation and all contributing scoring Manifest digests"); `contracts/delivery.md` §4.3 ("acceptance evaluation against exact generation and multiple scoring Manifest digests").
- **Failure scenario:** An Experiment registers Generation Operation G1 (Manifest M1). Later the owner adds Predictions. Exact resubmission of G1's `operation_key` with an extended source is a hard conflict (`contracts/platform.md` §1.5: "a reordered, truncated, extended, or otherwise changed source is a hard conflict"), so Whetstone must submit a second Generation Operation G2 with Manifest M2. The final-page hook legally inserts a second accepted `workflow_role=generation` relationship (the table key permits it) and clears the pointer. Reevaluation then must pin the accepted Manifest relationship set — but the evaluation row and `acceptance_id` digest hold exactly one `generation_manifest_digest`, and strict completeness is defined over "every Manifest Prediction" of that one Manifest. The evaluator either fails with no specified disposition or silently pins one Manifest and drops the other's Predictions from the expected set — an Experiment that appears valid while ignoring registered membership, exactly the "expected Prediction set … stable and enumerable" property the fresh interrogation is required to prove.
- **Evidence:** `docs/planning/platform-whetstone-refactor/v4/contracts/whetstone.md:169-188` (plural-keyed relationship table beside the singular evaluation digest field); `contracts/whetstone.md:136-141` (STRICT defined over "every Manifest Prediction", singular); `docs/planning/platform-whetstone-refactor/v4/contracts/delivery.md:119` (test matrix says "exact generation … Manifest digests", singular for generation); `docs/adr/0020-append-only-experiment-acceptance.md` (same singular/plural asymmetry). No sentence in the packet or ADRs forbids a second accepted generation relationship per Experiment.
- **Affected repositories:** whetstone-ai (acceptance schema and evaluator), dr-platform indirectly (registration-hook final-page contract feeds the relationship table).
- **Required correction:** the owner must choose one of two invariants and the packet must state it: (a) at most one accepted generation Manifest relationship per Experiment, enforced by a uniqueness constraint on `(experiment_name, workflow_role='generation')` and a hook rejection with a typed disposition, making an Experiment's Prediction membership fixed at first registration; or (b) plural `generation_manifest_digests` symmetric with scoring, with the expected Prediction set defined as the union of all accepted generation Manifests and the evaluation/`acceptance_id` digest extended accordingly. Either choice changes planned persistence or the Experiment contract; the current text supports neither deterministically.
- **Closure impact:** reopens the representability half of v3 P0-2 (and therefore v2 P0-5 / v1 P0-5) for a case the v3 synthesis did not walk; does not disturb v4 owner decisions 2 or 3.

## F2. A claimant that crashes between its late DBOS enqueue and its outcome CAS leaves a live workflow behind a terminal `NOT_ENQUEUED`-cancelled Attempt with no compensation row and no specified detector

- **Severity:** major
- **Class:** local-correction
- **Plan contract:** `contracts/platform.md` §1.5 cancellation ("When no DBOS row exists, finalization records `NOT_ENQUEUED`; it never describes DBOS's silent no-op as a delivered cancellation. If an in-flight claimant enqueues after Claim invalidation, its outcome CAS necessarily loses. It reloads the cancellation result, calls idempotent `cancel_workflow(…)` … and inserts or replays the append-only enqueue-compensation row before returning"); §1.5 missing-workflow policy; ADR 0005 (compensation clause); ADR 0019.
- **Failure scenario:** Cancellation intent commits and invalidates the outstanding Claim; the finalization transaction observes no DBOS row and records the Attempt terminal `CANCELLED` with `NOT_ENQUEUED`. The invalidated claimant's already-issued `DBOS.enqueue_workflow` call lands *after* that check (the DBOS call is explicitly outside application transactions, so no advisory lock serializes it), and the claimant process dies before its losing outcome CAS and before writing the compensation row. Result: a live DBOS workflow executes paid work while the platform's provenance says the Attempt was never enqueued. Every specified safety net misses it — compensation is performed only by the surviving claimant; the missing-workflow reclaim path applies only to unconfirmed *nonterminal* Attempts and the terminal row is immutable by trigger; the health report's "incomplete cancellation" keys off unresolved Attempt dispositions and unresolved compensation rows, and here neither exists; cancellation-request replay "returns the stored plan/results" without a stated re-verification of DBOS absence for `NOT_ENQUEUED` Attempts. The Operation also derives terminal `CANCELLED` (status precedence rule 3 keys only off unresolved Attempt cancellation dispositions), so `wait_operation` reports terminal while DBOS work runs. Domain rows the workflow persists do land (spend is not lost from Whetstone tables), but the platform record `NOT_ENQUEUED` is false, contradicting the contract's own promise that finalization never misdescribes the DBOS state, and an operator-confirmed replacement stacks duplicate spend on an execution the system claims never started.
- **Evidence:** `docs/planning/platform-whetstone-refactor/v4/contracts/platform.md:517-529` (compensation exists only on the claimant's own return path), `:534-543` (replay returns stored results; unresolved *compensation* — a row that exists — degrades health, but no row exists here), `:669-689` (missing-workflow recovery is defined for unconfirmed Attempts, not terminal ones), `:758-778` (status precedence rule 3), `:230-232` (terminal-Attempt immutability trigger); `docs/planning/platform-whetstone-refactor/v4/contracts/delivery.md:136-138` (the crash matrix tests cancel-then-late-enqueue only through a *surviving* claimant's compensation). DBOS 2.26.0 confirms the enqueue insert succeeds independently of any platform state (`_sys_db.py:669-705`).
- **Affected repositories:** dr-platform (cancellation finalization, health, request replay); whetstone-ai indirectly (duplicate generation spend).
- **Required correction:** add one bounded rule — either cancellation-request replay and the health scan must re-verify DBOS existence for every `NOT_ENQUEUED`-finalized Attempt of that request (a DBOS row found later inserts the compensation row and performs the idempotent cancel under the same ledger key), or the finalization `NOT_ENQUEUED` write must be re-checked by reconciliation whenever an Attempt's persisted `workflow_id` matches an existing DBOS row. Extend the §4.3 crash matrix with claimant-death-after-enqueue-before-CAS. No architecture changes; the compensation ledger and lock order absorb the fix.
- **Closure impact:** extends v3 P1-5 (which is otherwise closed); does not reopen the accepted overlap/undercount owner decisions — this workflow was never DBOS-cancelled, so ADR 0019's discarded-outcome clause does not cover it.

## F3. The acceptance-invalidation scope ("locks the Experiment") is well-defined only if Prediction identity stays experiment-scoped, and the packet never pins that requirement while inviting digest simplification

- **Severity:** minor
- **Class:** local-correction
- **Plan contract:** `contracts/whetstone.md` § "Experiment-acceptance schema and transaction" ("Every transaction that inserts a relevant Generation Run, Score Attempt, accepted … relationship, or required-profile change locks the Experiment, increments `acceptance_source_version`, and clears `current_acceptance_id`"); §2.3 ("Digest recipes may simplify where the old bytes forced awkward inputs"); ADR 0020; ADR 0001 (cross-Operation content-scoped convergence).
- **Failure scenario:** Today `stable_prediction_id` includes `experiment_name` (`whetstone-ai/src/whetstone/records/hashing.py:29-45`), so every Generation Run and Score Attempt maps to exactly one Experiment and the singular "locks the Experiment" is deterministic. The v4 identity section re-pins golden digests and explicitly allows recipe simplification without stating that Prediction identity must remain experiment-scoped. If a simplification drops `experiment_name` (plausible, since ADR 0001 celebrates cross-Operation convergence and nothing in the recipe inputs listed in §2.3 names the experiment), one content-scoped Generation Run becomes relevant to several Experiments; the outcome-persistence transaction then has no specified discovery rule for which Experiments to invalidate, no lock ordering over multiple Experiment rows (the packet orders Operations and the single Experiment only), and a foreign Operation's later success would leave another Experiment's pointer "current" against a stale highest-ordinal selection — silent wrongness the platform-cut check cannot catch because the foreign Operation is not in the pinned vector.
- **Evidence:** `whetstone-ai/src/whetstone/records/hashing.py:29-45` (experiment_name in the ID today); `docs/planning/platform-whetstone-refactor/v4/contracts/whetstone.md:42-55,211-214` (identity section and singular invalidation clause); `docs/adr/0001-content-scoped-execution-identity.md`.
- **Affected repositories:** whetstone-ai.
- **Required correction:** one sentence in `contracts/whetstone.md` §2.3 (and the golden-fixture gate) making experiment-scoped Prediction identity an explicit invariant of this cut — i.e., `experiment_name` remains an input to `prediction_id` so every domain outcome has exactly one owning Experiment — or, if the owner ever wants cross-Experiment sharing, a specified multi-Experiment relevance query and ascending Experiment lock order.
- **Closure impact:** none reopened; hardens v3 P0-2/owner decision 3 against a foreseeable identity change.

## F4. An evaluation cannot be persisted before the first Scoring Operation exists because the scoring-digest set is required non-empty

- **Severity:** minor
- **Class:** local-correction
- **Plan contract:** `contracts/whetstone.md` § "Experiment-acceptance schema and transaction" ("a canonically sorted non-empty set of scoring Operation/Manifest digests"); §2.4 ("The experiment-facing command reports both Operation statuses and one current append-only `ExperimentAcceptanceEvaluation`"); ADR 0018.
- **Failure scenario:** An Experiment whose generation Operation has completed but whose first Scoring Operation has not yet been registered (or a deliberately generation-only experiment) has zero accepted scoring Manifest relationships. Its strict evaluation is well-defined — `PARTIAL` with every required scoring cell `MISSING_SCORE`, all representable in the member tables — but the evaluation row itself cannot be inserted because `scoring_manifest_digests` must be non-empty, so no durable `PARTIAL` decision, no override provenance, and nothing for the experiment-facing command to report. The status surface silently degrades to "no evaluation exists," which is indistinguishable from "never evaluated."
- **Evidence:** `docs/planning/platform-whetstone-refactor/v4/contracts/whetstone.md:181-188` (non-empty constraint), `:195-202` (MISSING_SCORE cells exist independent of scoring Operations).
- **Affected repositories:** whetstone-ai.
- **Required correction:** allow an empty (still canonically sorted) scoring-digest set in the evaluation row and `acceptance_id` digest, or state explicitly that evaluation is defined only after at least one accepted scoring relationship and specify what the experiment command reports before then.
- **Closure impact:** refines v3 P0-2's representability requirement; nothing reopened.
