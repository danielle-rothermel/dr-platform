# v0 review findings — codex (code audit)

## F1. Terminal DBOS workflow failures have no path back into the item retry loop
- **Severity:** blocker
- **Spec section:** §1.5
- **Evidence:** src/dr_platform/submission.py:251 — resubmission only prepares retries for platform enqueue failures/stale claims before enqueueing; src/dr_platform/submission.py:581 — the claim loop only loads rows whose platform `enqueue_status` is `pending`; src/dr_platform/submission.py:551 — a successful DBOS enqueue immediately persists the item as `enqueued` or `workflow_already_present`; src/dr_platform/submission.py:734 — operation status is derived from enqueue-status counts, not DBOS workflow terminal state; src/dr_platform/observability.py:121 — DBOS workflow status is only read for an observability breakdown.
- **Consequence:** The spec says terminal-failed DBOS workflows retry on resubmit by incrementing `attempt`, but the current lifecycle has no reconciliation step that turns an item with `workflow_id=<failed workflow>` and `enqueue_status=enqueued` back into a claimable row. If the refactor only adds `attempt`/`workflow_id` columns and keeps the current submit shape, failed workflows remain completed platform items forever; if it increments attempts without a guarded reconciliation step, it risks duplicate live work.
- **Suggested change:** Add an explicit "reconcile terminal workflows" phase to §1.5 before claim: for each existing item with a workflow id, read the normalized DBOS status, leave active/success rows alone, and CAS terminal-failed rows to `pending` with `attempt = attempt + 1`, cleared library workflow fields, and a new claimable state. Specify the row predicate, DBOS statuses, and idempotency behavior under concurrent submitters.

## F2. The dedup contract names a non-DBOS status and omits live statuses that must block retries
- **Severity:** major
- **Spec section:** §1.5
- **Evidence:** src/dr_platform/dbos_config.py:33 — the local DBOS status enum is `PENDING`, `SUCCESS`, `ERROR`, `MAX_RECOVERY_ATTEMPTS_EXCEEDED`, `CANCELLED`, `ENQUEUED`, and `DELAYED`; src/dr_platform/dbos_config.py:43 — the current active set is `ENQUEUED`, `PENDING`, and `DELAYED`; .venv/lib/python3.12/site-packages/dbos/_core.py:403 — DBOS initializes non-queued workflows as `PENDING` and queued workflows as `ENQUEUED` or `DELAYED`.
- **Consequence:** The spec says "Dedup skips only ACTIVE/ENQUEUED/SUCCESS workflows." `ACTIVE` is not the status string this DBOS version returns, and `PENDING`/`DELAYED` are real live states. Implementing the spec literally would treat pending or delayed workflows as retryable terminal work, mint a fresh attempt, and duplicate an already-live workflow.
- **Suggested change:** Replace the prose status list with normalized categories based on the pinned DBOS strings: skip/block `PENDING`, `ENQUEUED`, `DELAYED`, and `SUCCESS`; retry only `ERROR`, `CANCELLED`, and `MAX_RECOVERY_ATTEMPTS_EXCEEDED`; define missing/unknown status behavior explicitly.

## F3. Queue priority verification is not provided by the DBOS enqueue path the plan uses
- **Severity:** major
- **Spec section:** §1.4
- **Evidence:** .venv/lib/python3.12/site-packages/dbos/_context.py:614 — `SetEnqueueOptions` accepts `priority`; .venv/lib/python3.12/site-packages/dbos/_dbos.py:1179 — `DBOS.enqueue_workflow` constructs `Queue(queue_name, database_backed_queue=True)`; .venv/lib/python3.12/site-packages/dbos/_queue.py:385 — database-backed queues return from `_validate_enqueue` before the `priority_enabled` check; .venv/lib/python3.12/site-packages/dbos/_queue.py:388 — the check that raises for priority on non-priority queues only runs after that early return.
- **Consequence:** The spec says platform queues are "verified at enqueue if DBOS exposes it," but this DBOS enqueue API does not validate `priority_enabled` for database-backed queue names. A misregistered queue can slip through the exact library-owned enqueue path the spec proposes, leaving the priority contract dependent on prior app setup and logs rather than a hard platform check.
- **Suggested change:** Make the platform enqueue helper explicitly retrieve the queue row before enqueue and assert `queue.priority_enabled is True` (or accept a registered `Queue` object instead of only `queue_name`). Add a spec note for missing queues and stale queue rows, and test the failure path.

## F4. Watermark export cannot be correct without new change-tracking columns or a snapshot protocol
- **Severity:** major
- **Spec section:** §1.6
- **Evidence:** src/dr_platform/db/schema.py:83 — operations currently have `created_at` and `completed_at`; src/dr_platform/db/schema.py:128 — items currently have only `created_at`; src/dr_platform/submission.py:661 — item outcome updates mutate enqueue status, metadata, and failure without updating any timestamp; src/dr_platform/submission.py:745 — operation summaries mutate status/counts/completed_at after item writes; src/dr_platform/backoff.py:168 — throttle state is the only platform table here with an explicit `updated_at`.
- **Consequence:** The spec requires incremental export of rows changed since a stored watermark, but the mutable platform rows that matter for analysis do not have a reliable per-row change cursor. A created-at watermark misses item status/failure/workflow-id updates; a completed-at watermark misses item-row changes and is vulnerable to concurrent writes around the export cutoff.
- **Suggested change:** Amend §1.3/§1.6 to add `updated_at` or a monotonic export sequence to every mutable kernel table, update it in every CAS/outcome/summary path, and define the export transaction semantics: read in a stable snapshot, export rows `<= snapshot_watermark`, then advance `<prefix>_export_state` only after the DuckDB/Neon writes commit. State the deletion/tombstone policy even if deletes are rare.

- **Spec section:** §1.1
- **Evidence:** /Users/daniellerothermel/drotherm/repos/whetstone-ai/src/whetstone/platform/graph_workflow.py:17 — whetstone imports `utc_now` from `dr_platform.backoff`; /Users/daniellerothermel/drotherm/repos/whetstone-ai/src/whetstone/platform/graph_workflow.py:336 — throttle delay calls still depend on that helper; /Users/daniellerothermel/drotherm/repos/whetstone-ai/src/whetstone/platform/graph_workflow.py:416 — failure recording also depends on it; /Users/daniellerothermel/drotherm/repos/whetstone-ai/tests/test_platform_graph_workflow.py:860 — tests monkeypatch `graph_workflow.utc_now` for deterministic timing.
- **Consequence:** Deleting `dr_platform.backoff.utc_now` without an explicit whetstone-side replacement breaks `graph_workflow` import and removes the current test seam for deterministic throttle timing. The spec says whetstone can define its own helper, but the implementation checklist does not point to the concrete runtime and test call sites that must move first.
- **Suggested change:** Add a small whetstone impact task before the dr-platform deletion: define a local `utc_now` or injected clock in `whetstone.platform.graph_workflow`, update the three call sites and tests, then delete the platform helper.
