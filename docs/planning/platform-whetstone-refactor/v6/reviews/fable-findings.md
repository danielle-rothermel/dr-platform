## F1. `NO_WORKFLOW_FOUND` is a durable final resolution that a delayed DBOS enqueue commit can silently falsify, leaving cancelled-intent work executing with no re-observation or specified claimant successor
- **Severity:** major
- **Class:** local-correction
- **Plan contract:** `contracts/platform.md` §1.5 bounded cancellation replay (`v6/contracts/platform.md:566-583`: "If the workflow remains absent through the configured missing-workflow grace period and observation count, replay records durable `NO_WORKFLOW_FOUND`. `SKIPPED_SHARED`, `NO_WORKFLOW_FOUND`, `CANCELLED`, and `OBSERVED_TERMINAL` are resolved hazards"), compensation idempotency (`platform.md:218-226`: closed dispositions; "Exact replay returns the existing row; an unequal workflow or reason for the same key is an integrity conflict"), new-reference guard (`platform.md:536-543`), `plan.md` lifecycle step 7 ("bounded missing-workflow observation resolves `NO_WORKFLOW_FOUND` rather than leaving an indefinite link hazard") and unified invariant 7; ADR 0019; ADR 0021.
- **Failure scenario:** Claimant C for Operation A commits `enqueue_call_started_at` for Claim K on workflow W, issues the DBOS enqueue, and is then suspended mid-call (laptop lid close, VM pause, or a stalled TCP connection to the DBOS system database — all realistic in the owner's dev environment, and a Postgres INSERT can commit server-side minutes after the client last made progress). Cancellation of A invalidates K and finalizes the Attempt terminal `NOT_ENQUEUED`. Bounded replay inspects K, observes no DBOS row for W through the configured grace period and observation count (defaults ≈ 60s × 3), and records durable, resolved `NO_WORKFLOW_FOUND`, which "unblocks new-reference creation" and clears health. The suspended enqueue then commits: W now exists `ENQUEUED`, is dequeued, and executes a paid generation/scoring workflow whose cancellation was operator-confirmed. Two terminal sub-cases: (a) C dies on resume — no actor ever re-observes W; the compensation ledger durably asserts a workflow that demonstrably exists was never found, health is green, no physical cancellation ever occurs, and the cancelled-intent execution runs to completion at full provider cost, persisting an append-only domain row that bumps the Experiment source version yet can never be accepted (its Attempt is terminal `NOT_ENQUEUED`/`CANCELLED`, so strict promotion rejects it as `EXECUTION_INCOMPATIBLE`) — silently duplicated paid work plus a durable ledger/reality contradiction; (b) C resumes and loses its outcome CAS — the contract routes it to "insert or exact-reload compensation using its durable key", but the row is already resolved `NO_WORKFLOW_FOUND`; the contract defines no successor behavior for a claimant that knows its enqueue succeeded while its compensation is already resolved as workflow-not-found (proceeding to cancel would mutate a resolved disposition outside the closed transition set; stopping preserves outcome (a)). The design's implicit assumption — that an enqueue call unobservable for the full grace window will never subsequently commit — is unstated and unenforceable: the installed DBOS enqueue is an unfenced idempotent insert keyed only by workflow ID (`_sys_db.py:649-650,896-910`), and no client-side timeout can prevent a server-side commit. ADR 0019 accepts *labeled* provider-call overlap; it does not cover an entire workflow executing after the system durably concluded it does not exist.
- **Evidence:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/platform.md:566-583` (replay resolves durable `NO_WORKFLOW_FOUND`; resolved hazards are final and unblock linking; nothing re-observes a resolved hazard), `:218-226` (closed compensation dispositions, exact-replay-or-integrity-conflict, immutable identity/call-start facts), `:536-543` (guard checks only *unresolved* compensation), `:729-754` (missing-workflow policy for live Attempts has repeated-observation protection, but it does not apply to a terminal `NOT_ENQUEUED` Attempt with resolved compensation); `/Users/daniellerothermel/drotherm/repos/dr-platform/.venv/lib/python3.12/site-packages/dbos/_sys_db.py:649-650` and `:896-910` (enqueue is a plain system-DB status write with no fencing token; commit timing is independent of any application-side observation); `v6/contracts/delivery.md:166-176` gates prove hazard resolution and post-resolution linking but contain no fixture in which the enqueue commit lands *after* `NO_WORKFLOW_FOUND` resolution.
- **Affected repositories:** dr-platform (compensation lifecycle, cancellation replay/health contract, delivery §4.3/§4.4 fixtures); whetstone-ai as the payer for the silently executing cancelled work.
- **Required correction:** Keep the bounded link-guard resolution, but stop treating `NO_WORKFLOW_FOUND` as unfalsifiable: (1) specify that bounded health/cancellation reconciliation periodically re-observes `NO_WORKFLOW_FOUND` compensations by their durable workflow IDs and, when the workflow has since appeared, records an append-compatible successor fact (e.g., a `LATE_ENQUEUE_OBSERVED` resolution row or a defined `NO_WORKFLOW_FOUND → CANCELLED/SKIPPED_SHARED/OBSERVED_TERMINAL` escalation) and re-runs the exclusivity-checked cancellation; (2) specify claimant behavior when its enqueue succeeded but its compensation is already resolved `NO_WORKFLOW_FOUND` — it must escalate through the same path, not integrity-conflict or silently stop; (3) add the delayed-commit fixture (suspend claimant, resolve `NO_WORKFLOW_FOUND`, land the enqueue, run health/claimant, prove the workflow is cancelled if exclusive or `SKIPPED_SHARED` if referenced, and prove the ledger records the late appearance). Alternatively the owner may explicitly accept the residual orphan execution as an ADR-0019-style cost — but then the contract and health/inspection language must stop implying resolved hazards are correct, and the accepted silent-spend window must be stated.
- **Closure impact:** none reopened — v5 L3's decidable-guard requirement is met as specified; this is a new bounded residual in the same hazard-resolution mechanism (the guard is decidable but its `NO_WORKFLOW_FOUND` decision is falsifiable and has no successor).
- **Convergence signal:** possible non-convergence

## F2. The populated-only `PARTIAL` predicate is not one exact end-to-end rule: its SQL semantics are locale/ctype-dependent and whetstone's retained Python scoring guard uses a different whitespace definition
- **Severity:** minor
- **Class:** local-correction
- **Plan contract:** `plan.md` accepted owner policy 10 ("The one canonical persisted-output predicate is `terminal_submission_text IS NOT NULL AND terminal_submission_text ~ '[^[:space:]]'` … selection, identity, retry, Manifest, outcome, and narrowed deletion parity share the same boundary"); `contracts/whetstone.md:129-142` and `:353-368`; `contracts/delivery.md:149-156`; traceability V6 owner decision V5-OD1 ("one observable contract").
- **Failure scenario:** Postgres `[[:space:]]` is evaluated per the database ctype: under `C`/`C.UTF-8` it matches only the six ASCII whitespace characters, while under glibc UTF-8 locales it matches a wider (but still not Python-equal) set; the contract never pins the ctype, so "the exact persisted predicate" denotes different candidate sets on differently-initialized databases. Separately, the live scoring path's own populated check is Python `str.strip()` (`whetstone-ai/src/whetstone/platform/scoring.py:265-267`: `if not run.summary.terminal_submission_text.strip(): raise … "partial generation run missing terminal_submission_text"`), and v6 retains Whetstone's "append-only result persistence" scoring domain code without aligning or removing this guard. Python treats U+00A0/U+2007/U+3000 etc. as whitespace; glibc `iswspace` does not classify U+00A0 as space and `C` ctype classifies no non-ASCII character. Concrete walk: a `PARTIAL` Generation Run whose `terminal_submission_text` is exactly `" "` (a plausible LM emission) satisfies the SQL predicate, enters the selection digest, scoring Item identity, and Manifest — yet the scoring step raises at the retained guard, producing retries under `RetryPolicy` and a terminal failure/harness outcome. That directly contradicts policy 10's claim that whitespace-only rows "never receive scoring Item identity, retry behavior, or a scoring outcome" and quietly splits the boundary that selection, retry, outcome, and deletion parity are required to share. The failure is visible (typed error), not silent, but it burns paid retries and makes the deletion-parity gate ambiguous for exactly the character class the fixtures (all ASCII: empty/space/tab/newline) never exercise.
- **Evidence:** `/Users/daniellerothermel/drotherm/repos/whetstone-ai/src/whetstone/platform/scoring.py:265-267` (Python-whitespace guard); `/Users/daniellerothermel/drotherm/repos/whetstone-ai/src/whetstone/records/models.py:217` (`terminal_submission_text: StrictStr`, non-null, so the boundary is carried entirely by the whitespace test); `v6/contracts/whetstone.md:129-142,353-368` and `v6/contracts/delivery.md:149-156` (fixtures cover only ASCII whitespace; no ctype/collation pin; no requirement to align or delete the Python guard).
- **Affected repositories:** whetstone-ai (scoring selection/guard, fixtures); dr-platform docs (`plan.md` policy 10, ADR 0018 predicate sentence); the fresh-database provisioning contract in delivery.
- **Required correction:** Pin the predicate's execution semantics (declare the fresh application database ctype, or replace the POSIX class with an explicit character-set predicate that is ctype-independent); make the same normative rule govern the retained Python-side guard (align it to the pinned predicate or delete it in the replacement path so SQL selection is the sole boundary); add a non-ASCII-whitespace-only `PARTIAL` fixture (e.g., U+00A0) asserting the identical decision at selection, identity, retry, outcome, and deletion-parity layers.
- **Closure impact:** bounded gap in the execution of V5-OD1 ("one exact end-to-end observable rule"); it does not reopen the owner decision itself — populated-only selection and the narrowed parity boundary remain coherent.
- **Convergence signal:** none

## F3. Pinned Analysis Bundle reads have no retention or failure contract: a newer promotion plus cleanup can remove the version COPRO is pinned to mid-iteration
- **Severity:** minor
- **Class:** verification-gap
- **Plan contract:** `contracts/whetstone.md:369-381` (COPRO "captures the committed bundle ID/`snapshot_seq` and reads … through a pinned local-DuckDB Analysis adapter … it refuses to drift to a newer bundle during the iteration"); `contracts/publication.md:85-103` (Lease/cleanup: "Only the current token holder may delete uniquely named bundle stages from older expired tokens … Cleanup … never deletes a version referenced by the current pointer"; readers "resolve only that pointer").
- **Failure scenario:** COPRO iteration i exports, pins bundle B(n), and begins candidate reads. A second export (cron or ad hoc — the contract permits both) promotes B(n+1); B(n) is no longer referenced by the current pointer, so the cleanup rule's only stated protection no longer covers it, and the current token holder may delete its versioned tables. COPRO's next pinned read against B(n) fails mid-iteration. The failure is loud (missing table), not silent wrongness, but the packet defines neither a retention guarantee for recently promoted non-current versions nor a typed pinned-read failure/retry behavior for the one consumer it explicitly instructs to pin — so the wait→export→pinned-read gate can pass in isolation while the composed system races.
- **Evidence:** `v6/contracts/whetstone.md:369-381`; `v6/contracts/publication.md:85-103` (retention stated only for the current-pointer version); no retention/failure clause anywhere in `publication.md` §1.6/§4.1 or `delivery.md` gates 6/9 covers a pinned non-current version.
- **Affected repositories:** dr-platform (export/cleanup contract), whetstone-ai (COPRO adapter behavior).
- **Required correction:** State the rule: either promoted bundle versions are retained for a declared window/count (and cleanup may only remove versions older than that), or pinned readers must tolerate deletion with a typed `PINNED_BUNDLE_GONE` failure and a defined restart-at-new-pin behavior; add one fixture exercising promotion-plus-cleanup during a pinned iteration.
- **Closure impact:** none.
- **Convergence signal:** none

## F4. The scoring-selection freeze sentence still reads as choosing one run per Prediction while the parity clauses require plural-run Manifest membership (identified during closure)
- **Severity:** minor
- **Class:** local-correction
- **Plan contract:** `contracts/whetstone.md:179-187` ("both scoring-selection freeze and acceptance choose the `SUCCESS` Generation Run with the highest platform Attempt ordinal…") versus `:129-142` ("selects eligible `SUCCESS` runs and only `PARTIAL` runs whose…", plural) and `:353-368` ("The replacement Manifest must match the deliberately narrowed retained set: every status-eligible `SUCCESS` plus only [populated] `PARTIAL` rows").
- **Failure scenario:** An implementer reading `whetstone.md:179-187` builds the frozen scoring selection with exactly one run per Prediction (the then-accepted highest-`SUCCESS` ordinal), because the sentence says the *freeze* "chooses" that run; an implementer reading `:353-368` includes every eligible `SUCCESS` plus populated `PARTIAL` run. The two produce different selection digests, different Scoring Operation identities, and materially different paid scoring scope. V6's run pinning (L2) makes both readings acceptance-safe — other-run candidates become `SUPERSEDED_GENERATION` and stale pins fail closed as `MISSING_SCORE` — and the §2.5 parity fixture would fail the single-run reading, so this cannot produce silent acceptance wrongness; it is the surviving wording half of v5 Fable F1's internal-contradiction note. But a normative sentence that a mandatory gate contradicts is a defect in the contract, not a style issue: the freeze sentence should say what it means (the freeze *derives the accepted run for cell pinning*; Manifest *membership* is the narrowed parity set).
- **Evidence:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/whetstone.md:129-142,179-187,353-368`.
- **Affected repositories:** whetstone-ai contract text only.
- **Required correction:** Rewrite `whetstone.md:179-187` to separate the two rules explicitly: (1) scoring Manifest membership is the populated-only narrowed candidate set (plural runs per Prediction permitted); (2) the freeze and the evaluation both derive the accepted run per Prediction — highest successful ordinal in the single accepted lineage at their respective cuts — and the cell-pinning/`SUPERSEDED_GENERATION` rules govern any divergence between those cuts.
- **Closure impact:** bounded residual of v5 Fable F1's wording note; the core run-pinning/totality closure stands.
- **Convergence signal:** none
