## F1. The acceptance schema cannot represent an explicitly policy-accepted `PARTIAL` Generation Run
- **Severity:** blocker
- **Class:** architecture-changing
- **Plan contract:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/whetstone.md` §2.4 and “Experiment-acceptance schema and transaction”; ADR 0018 strict Experiment acceptance; ADR 0020 append-only Experiment acceptance
- **Failure scenario:** A populated `PARTIAL` Generation Run is scoring-eligible and an operator-confirmed persisted partial policy explicitly accepts that run, which the winner contract says must pin the run for its scoring cells. The generation-member schema, however, permits only `MISSING`, `REJECTED`, and `SELECTED_SUCCESS`, and only `SELECTED_SUCCESS` may carry a non-null selected `generation_run_id`. The evaluator must therefore either record the accepted `PARTIAL` run as `SELECTED_SUCCESS` (falsifying its domain status), omit the selected run (making run-pinned scoring and exact platform-Attempt proof unreproducible), or reject a policy outcome the contract explicitly permits. Strict acceptance itself can work, but the advertised explicit-partial path cannot be persisted truthfully.
- **Evidence:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/whetstone.md:200-202` explicitly permits a persisted policy to accept and pin a `PARTIAL` Generation Run, while `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/whetstone.md:265-271` defines no selected-partial disposition and allows a selected run only for `SELECTED_SUCCESS`; `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/adr/0018-strict-experiment-acceptance.md:13-18` preserves the same explicit-policy exception.
- **Affected repositories:** `whetstone-ai` acceptance schema, evaluator, identity, and exported acceptance truth; `dr-platform` only through the selected exact Attempt/cut references consumed by Whetstone; Unitbench/Analysis readers can receive a falsely labeled or unrepresentable evaluation
- **Required correction:** Add a truthful selected-partial-policy state (or a status-bearing selected disposition model) that permits the exact selected Generation Run and Operation/Item/Attempt references only with a matching immutable policy authorization. Bind the observed `PARTIAL` status, policy digest, selected run, platform `SUCCEEDED`/DBOS `SUCCESS` proof, scoring-cell pinning, candidate provenance, matrix, and `acceptance_id`; add schema checks and strict-versus-override fixtures.
- **Closure impact:** reopens the representable-acceptance portion of v3 P0-2, v2 P0-5, v1 P0-5, and retained strict/stratified owner policy; otherwise none
- **Convergence signal:** possible non-convergence

## F2. `NO_WORKFLOW_FOUND` can resolve compensation while the independently committed DBOS enqueue is still in flight
- **Severity:** blocker
- **Class:** architecture-changing
- **Plan contract:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/platform.md` §1.5 cancellation and missing-workflow policy; ADR 0005 reference-aware cancellation; ADR 0021 append-only enqueue Claim identity
- **Failure scenario:** Claim A durably crosses `enqueue_call_started_at`, calls DBOS outside the application transaction, and blocks inside DBOS's independent `init_workflow` transaction before its insert commits. Cancellation invalidates A and terminalizes the local Attempt `NOT_ENQUEUED`. While A is still blocked, reconciliation repeatedly observes no committed DBOS row and, after the finite grace/count, records resolved `NO_WORKFLOW_FOUND`, clearing the new-reference guard. The DBOS transaction then unblocks and commits `ENQUEUED`; A dies after that commit but before `init_workflow` returns or the application outcome CAS runs. Because the compensation was already resolved from absence and the claimant never reaches its losing CAS, no unresolved Claim remains for replay, so the workflow can run as unreferenced paid work. A finite series of absence observations did not prove that an enqueue already past the call boundary could no longer appear. DBOS cancellation cannot pre-place a tombstone because its public implementation only updates an existing row.
- **Evidence:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/platform.md:565-581` treats repeated absence as resolved `NO_WORKFLOW_FOUND` and unblocks references, while `:730-749` acknowledges the split application/DBOS transactions. Installed DBOS records enqueue in its own `engine.begin()` transaction and returns only after that transaction exits at `/Users/daniellerothermel/drotherm/repos/dr-platform/.venv/lib/python3.12/site-packages/dbos/_sys_db.py:3966-3991`; the insert/upsert is `/Users/daniellerothermel/drotherm/repos/dr-platform/.venv/lib/python3.12/site-packages/dbos/_sys_db.py:633-703`. Missing-row cancellation is only an `UPDATE`, so it creates no future-enqueue guard, at `/Users/daniellerothermel/drotherm/repos/dr-platform/.venv/lib/python3.12/site-packages/dbos/_sys_db.py:845-878`.
- **Affected repositories:** `dr-platform` Claim, cancellation, compensation, reconciliation, and DBOS adapter lifecycle; `whetstone-ai` generation/scoring paid-work safety and accounting
- **Required correction:** Do not make absence alone terminal proof for a call-started Claim. Introduce a protocol that establishes enqueue-call quiescence or a durable DBOS-side guard/tombstone before resolving the hazard, or keep the Claim unresolved for explicit operator repair when quiescence cannot be proven. The correction must preserve reference locks, `SKIPPED_SHARED`, exact Claim replay, and bounded operability without allowing a later commit; gate a deliberately blocked DBOS insert that commits after the current grace window, then kill the claimant after DBOS commit but before return/outcome CAS.
- **Closure impact:** Fable F2 and its L3 hazard-resolution target remain open; reopens the claimant-death/cancellation-safe portions of v4 L1, v3 P1-5, and v1 P0-4; durable Claim identity itself is closed
- **Convergence signal:** possible non-convergence

## F3. Cross-family `snapshot_seq` equality cannot prove compatible application and DBOS source cuts
- **Severity:** major
- **Class:** architecture-changing
- **Plan contract:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/publication.md` §1.6 export flow and §4.1 two-plane table inventory; ADR 0008 destination-local export state; ADR 0015 two-plane stores
- **Failure scenario:** Export captures application Postgres `snapshot_seq=H` under the Export Barrier and releases that source snapshot. A DBOS workflow changes state afterward, before the independently timed DBOS telemetry snapshot is read. The Whetstone/application bundle reflects the earlier application cut while the DBOS bundle reflects the later DBOS state, yet both are labeled with the export's `snapshot_seq=H`. A future cross-family reader using `REQUIRE_COMPATIBLE_SNAPSHOT(max_snapshot_seq_skew=0)` accepts them as the “same source cut” and can silently join an application Attempt state from before H with DBOS telemetry from after H. Destination fencing prevents stale promotion but cannot create a transactionally shared cut across two databases.
- **Evidence:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v6/contracts/publication.md:31-37` defines the DBOS projection as an independently captured full DBOS snapshot; `:73-80` derives `snapshot_seq` from Operational Postgres; `:138-143` again calls DBOS telemetry independently timed; and `:231-249` makes cross-family compatibility depend on `snapshot_seq`, explicitly defining skew `0` as the same source cut.
- **Affected repositories:** `dr-platform` export metadata and snapshot-read policy; `whetstone-ai` Analysis publication; future Unitbench/kernel/DBOS diagnostic readers that rely on compatible-snapshot checks
- **Required correction:** Give each independently captured source a truthful cut coordinate and make cross-source compatibility policy explicit. Either coordinate application and DBOS capture with a real causal barrier/check, or prohibit `snapshot_seq` equality from proving same-cut compatibility and require a declared temporal/causal tolerance with both source coordinates. Add a race fixture in which DBOS changes after the application cut but before telemetry capture.
- **Closure impact:** reopens v2 P0-4, retained v3 owner decision 2, and the prior rows that declared cross-family checked skew coherent; atomic per-bundle promotion and destination fencing remain closed
- **Convergence signal:** possible non-convergence
