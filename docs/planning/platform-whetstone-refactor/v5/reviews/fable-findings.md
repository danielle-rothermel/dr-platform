## F1. The scoring-cell winner rule is not pinned to the accepted Generation Run and is not total, so a score of a superseded or `PARTIAL` run can silently satisfy — or nondeterministically tie for — a strict-acceptance cell
- **Severity:** blocker
- **Class:** owner-decision
- **Plan contract:** `contracts/whetstone.md` §2.4 (strict predicate, line 153: scores are required "for each accepted run"; winner rule, lines 184-191; freeze rule, lines 174-178; `PARTIAL` eligibility, lines 129-137; candidate table, lines 263-271), `plan.md` accepted owner policies 9 and 10 (lines 210-224), ADR 0018 (lines 15-18), ADR 0020 (lines 18-20), whetstone `CONTEXT.md` "Score Attempt" (lines 61-68).
- **Failure scenario:** Two concrete walkthroughs, both using flows the packet itself mandates. **(a) Stale relationship wins.** Prediction P's Generation Run r0 (Attempt 0) is cancelled locally, the shared execution later succeeds so r0 is a persisted domain `SUCCESS`, and a confirmed `OPERATOR_CANCEL_RETRY` produces r1 (Attempt 1, `SUCCESS`) — the exact "shared late success plus cancel/retry" fixture in `contracts/delivery.md:155-156`. Scoring relationship S1 (ordinal 1) scored r0 for profile π: `ScoreAttemptStatus.SUCCESS`. S2 (ordinal 2) scores r1 but its only candidate harness-fails. At evaluation the accepted run is r1 (highest ordinal, policy 6/8). For cell (P, π) the normative rule — "the newest relationship … that has at least one successful candidate", then "the successful Score Attempt with the highest platform Attempt ordinal" (`whetstone.md:184-191`) — selects S1's success, which scored **r0**. The cell is marked `ACCEPTED` while the strict predicate (`whetstone.md:153`) requires a `SUCCESS` score *of the accepted run r1*; the generation member names r1 while the scoring member's selected Score Attempt references r0. Strict acceptance is satisfied silently with a score of an output that is not the accepted one. **(b) Within-relationship tie.** Under OD3, one frozen selection contains both populated-`PARTIAL` r0 and `SUCCESS` r1 for P (`whetstone.md:131` submits "eligible `SUCCESS` and populated `PARTIAL` Generation Runs"; parity gate `whetstone.md:325-332`), producing two scoring Items for the same logical cell — Item(r0,π) and Item(r1,π) — in one Scoring Operation. Both score attempts succeed at platform Attempt ordinal 0. "Highest successful platform Attempt ordinal within that relationship" compares ordinals **across two different Item lineages**: 0 ties 0, and no tiebreak exists; worse, if Item(r0,π) harness-failed once and succeeded at ordinal 1, the rule deterministically prefers the retried score of the *non-accepted `PARTIAL`* run over the first-try score of the accepted run. This is precisely the "equal Attempt ordinal with different recipes" case the test contract names (`contracts/delivery.md:132-137`) but the design cannot decide. Note also the internal contradiction: `whetstone.md:174-178` says the scoring-selection freeze chooses *the* single highest-`SUCCESS` run per Prediction, while `whetstone.md:131` and `whetstone.md:325-332` require the freeze to reproduce the multi-run rescore candidate set including `PARTIAL`; both cannot hold as written.
- **Evidence:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v5/contracts/whetstone.md:129-137,150-156,174-191,246-254,263-271,325-332`; `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v5/plan.md:210-224`; `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/adr/0018-strict-experiment-acceptance.md:15-18`; `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/adr/0020-append-only-experiment-acceptance.md:18-22`; `/Users/daniellerothermel/drotherm/repos/whetstone-ai/CONTEXT.md:61-68`. Live-code support for the multi-run candidate premise: the current selector filters plural "allowed Generation Run statuses" and the packet freezes parity to it (`/Users/daniellerothermel/drotherm/repos/whetstone-ai/src/whetstone/platform/rescoring.py:67,622,711`; `plan.md:71-74`). The scoring-member cell key is Prediction-scoped, not run-scoped (`whetstone.md:246-254`), and the candidate disposition set (`SELECTED`, `SUPERSEDED_RELATIONSHIP`, `SUPERSEDED_ATTEMPT`, `REJECTED`) has no state for a candidate that scored a non-accepted run (`whetstone.md:263-271`).
- **Affected repositories:** whetstone-ai (acceptance schema/evaluator, scoring selection freeze), dr-platform docs (`plan.md` policy 9/10, ADR 0018/0020, `CONTEXT.md` glossaries), and the delivery test contract; the dr-platform kernel itself is unaffected.
- **Required correction:** Pin each logical scoring cell to a target Generation Run before candidate selection. The owner must ratify one rule; the strict predicate already implies the default: a cell's eligible candidates are only Score Attempts whose `generation_run_id` equals the evaluation's selected accepted run for that Prediction (or a run explicitly authorized by the persisted partial/override policy, e.g. a policy-accepted `PARTIAL` run). Candidates scoring any other run persist with a new immutable disposition (e.g. `SUPERSEDED_GENERATION`) and can never satisfy or win a cell. With the run pinned, all within-relationship candidates for a cell share one Item lineage, making "highest successful platform Attempt ordinal" total, and the newest-relationship rule then operates only on run-matched candidates, restoring OD2's determinism. Amend `plan.md` policy 9, `whetstone.md` §2.4 (winner rule and freeze sentence — reconcile the single-run freeze clause with the multi-run parity clause), ADR 0018/0020, both glossary entries, and add two fixtures to `contracts/delivery.md` §4.3/§4.4: (i) regeneration-after-scored-success proving the stale relationship's success cannot satisfy the new accepted run's cell, and (ii) `PARTIAL`+`SUCCESS` coexistence in one selection proving the cell winner is run-matched and total.
- **Closure impact:** reopens the Codex F2 / OD2 closure (deterministic Score Attempt selection is not total on the packet's own candidate space) and, through it, the v4 rows that declared v2 P0-5/P1-6 and v1 P0-5 resolved by OD2. OD3 remains closed (eligibility itself is coherent) but its interaction with the winner rule is the trigger for scenario (b).

## F2. Enqueue-compensation cancellation ignores the reference-exclusivity predicate, so the repair path can physically cancel a content-shared workflow that another Operation legitimately references
- **Severity:** major
- **Class:** local-correction
- **Plan contract:** `contracts/platform.md` §1.5 (exclusivity predicate and racer guard, lines 506-515; claimant late-enqueue compensation, lines 521-529; bounded cancellation replay, lines 531-539) versus ADR 0005 (lines 3-6: physical DBOS cancellation "only when no other live Operation references that content-scoped execution"; lines 28-30 carve the compensation path with no such predicate).
- **Failure scenario:** Operation A's Attempt for content-scoped `workflow_id` W is claimed; cancellation of A invalidates the Claim and finalizes the Attempt terminal `NOT_ENQUEUED` (no DBOS row observed). The finalized disposition means no *unresolved* DBOS-cancellation intent remains on any Attempt referencing W, and no compensation row exists yet (it is created only on discovery). Operation B now submits the same content: its link/create path takes the workflow advisory lock, finds no unresolved intent (`platform.md:510-515`), enqueues or links W legitimately, and B's Attempt goes `ENQUEUED`/`ACTIVE`. Later, either the slow invalidated claimant of A wakes and follows `platform.md:521-529`, or bounded replay follows `platform.md:531-539`: each sees a terminal `NOT_ENQUEUED` Attempt whose persisted workflow now exists in DBOS with no resolved compensation row, inserts the compensation ledger row, and "issues the same idempotent non-recursive cancellation" — physically cancelling W while Operation B holds a live, registered, nonterminal reference to it. B's active (possibly paid) work is killed by another Operation's repair machinery; B's Attempt then finalizes sticky `CANCELLED` with foreign provenance and needs a confirmed operator retry, and a replacement may duplicate provider spend. This directly violates the exclusivity invariant the same section defines for the operator path (`platform.md:506-509`) and ADR 0005's headline rule. The only alternative reading — that a `NOT_ENQUEUED`-finalized Attempt with an invalidated Claim counts as *unresolved* intent forever, blocking B's link — is also defective: when the claimant died *before* ever calling DBOS, no row will ever appear, no compensation row is ever created, and the contract defines no event that resolves the hazard, so the same content becomes permanently unlinkable. Both readings break a stated invariant; the contract must choose and specify.
- **Evidence:** `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/planning/platform-whetstone-refactor/v5/contracts/platform.md:506-539`; `/Users/daniellerothermel/drotherm/repos/dr-platform/docs/adr/0005-reference-aware-cancellation.md:3-6,25-30`. The delivery test contract covers late-enqueue and claimant-death compensation (`contracts/delivery.md:150-154`) but has no case where a legitimate new reference attaches between Claim invalidation and compensation, so the defect would also pass every specified gate — a companion verification gap.
- **Affected repositories:** dr-platform (cancellation/compensation transactions, compensation ledger dispositions, delivery test contract); whetstone-ai only as the affected caller of shared content-scoped executions.
- **Required correction:** (1) Both compensation issuers — the surviving claimant (`platform.md:521-529`) and bounded replay/health reconciliation (`platform.md:531-539`) — must acquire the same advisory-workflow-lock-then-Operation-row order and re-evaluate the reference-exclusivity predicate of `platform.md:506-509` before any physical `cancel_workflow` call; when another registered, nonterminal current-Attempt reference exists, the compensation row is inserted/replayed with a `SKIPPED_SHARED`-style `cancel_disposition` and no DBOS call is made. (2) Define the resolution event for the late-enqueue hazard on a `NOT_ENQUEUED` Attempt with an invalidated Claim (e.g., a resolved compensation row — including a `NO_WORKFLOW_FOUND` disposition written by bounded replay after the missing-workflow grace window — clears the hazard), so new-reference creation has a decidable guard instead of an ambiguous "unresolved intent". (3) Add the race fixture to `contracts/delivery.md` §4.3: cancel A, invalidate Claim, let B link/enqueue the same content, run claimant and replay compensation, and assert B's workflow is never physically cancelled and B's Attempt stays live.
- **Closure impact:** none reopened — L1 (claimant-death discovery) remains closed as specified; this is a new adjacent defect in the same repair mechanism and in ADR 0005's compensation carve-out.

## Verdict
- **Gate:** REPEAT_CONVERGENCE
- **Reason:** Mechanical conditions are met: F1 is a blocker and an unresolved owner decision (OD2's determinism claim fails on the packet's own candidate space and contradicts the strict-acceptance predicate), so a v4 source finding (Codex F2) and the v4 rows it governed (v2 P0-5/P1-6, v1 P0-5) are not closed with evidence; F1 changes acceptance-selection state (candidate disposition taxonomy and cell/run binding) in whetstone-ai. F2 additionally shows the cancellation-compensation repair contradicting ADR 0005's core invariant, a correctness defect in lifecycle state handling. Everything else audited — singular membership, pre-scoring evaluations, `PARTIAL` eligibility, restart-safe targets, currentness, publication fencing, two-plane readers, cutover order, and every installed-DBOS feasibility claim — is coherent, so a successor draft resolving F1's run-pinning rule and F2's exclusivity/resolution predicates should be a bounded revision.
- **Unverified:** (1) All live-store, load, parity, and end-to-end obligations remain unexecuted implementation gates, exactly as declared: MotherDuck conditional lease/atomic replacement, Neon pooling/compute-suspension transaction behavior, local DuckDB `fcntl.flock` crash behavior, Vercel Node runtime/secret wiring, OTLP degradation, same-millisecond dequeue variance staying inside the mixing bound, Experiment-row-lock load thresholds, corrected rescore parity, and COPRO/zero-spend wait→export→pinned-read continuity. Proof required is the named live/crash/contract/parity/load/e2e test in `delivery.md` §4.3-§4.4 on the locked revisions. (2) F2's failure walkthrough depends on which of two readings of "unresolved DBOS-cancellation intent" (`platform.md:511-515`) is intended; I show both readings defective (shared-work cancellation versus permanent fail-closed linking), but the intended reading should be confirmed by the owner when specifying the correction. (3) No test suites were run (read-only review); repository verification commands in `delivery.md` §4.5 were checked for existence (`scripts/ci/{lint,unit,integration}.sh`, pnpm scripts) but not executed.
