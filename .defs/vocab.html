The dr-platform staged-work pipeline contract

A reference for the terms and guarantees that bind dr-platform.

dr-platform · 2026-07-24

This is the vocabulary of the staged-work pipeline dr-platform implements: the terms, the guarantees that bind this repo, what is in and out of scope, and the mapping from each term to the names actually exported by dr_platform.

Terms

TermDefinition
WorkOne application-owned unit of logical activity that the platform schedules and tracks; the platform never inspects what the work means.
ReferenceAn opaque immutable string the platform stores and passes through, and never interprets or resolves; the caller alone knows what it points at.
QueueAn application-owned DBOS queue that a stage names; the platform enqueues a stage's workflow onto it but does not own or configure it.
WorkflowA DBOS durable execution unit that runs a stage callable; after a crash DBOS may replay its body, so its side effects are expected to tolerate re-execution.
AttemptOne row in an ordered, append-only sequence recording a single try at running a stage's workflow; rows are never overwritten, and a new one is added for each fresh try.
ControlA persisted row governing admission for one stage, carrying a capacity bound and a paused flag; admission consults it before letting new work in.
SelectorAn exact-label match predicate on a control that decides which work items the control governs; a control matches work whose labels contain every selector key/value pair exactly, the work may carry additional labels, and the empty selector still matches every item at its stage.
CapacityThe desired count of concurrently admitted stage executions a control allows; a target occupancy bound, not a worker count and not a request-rate or token limit.
TerminalA permanently settled state or record. Terminal attempt rows, SUCCEEDED, and CANCELLED are never reopened or overwritten; a terminal FAILED stage stays FAILED unless an explicit operator retry or cancellation supersedes it — the platform never reopens a terminal state on its own.
IdempotentA property of an operation that, when the same call is replayed, safely does nothing further or self-heals rather than duplicating its effect.
DurabilityThe property that an interrupted stage body resumes under one fixed attempt identity after a crash, without creating a new attempt (DBOS replay).
ColocationThe platform's tables and the DBOS system schema sharing one PostgreSQL database, so stage outcome and the next stage can commit in a single transaction.
Pipeline DefinitionOne immutable, versioned, non-empty ordered sequence of pipeline stages declaring a linear pipeline, identified by a pipeline key plus a positive integer version and validated to have unique stage keys.
Pipeline StageOne ordered scheduling-and-durability step in a linear pipeline, naming an application-owned queue, a stage callable, and an args_for adapter that turns immutable submission facts into workflow arguments; it is never a graph node.
Pipeline IdentityThe pipeline key and version pair that identifies one immutable pipeline definition across the registry; a small frozen value carrying the key and version, not a reference or hash.
Pipeline RegistryAn in-memory registry, populated from authoritative startup declarations, that maps each pipeline identity to exactly one pipeline definition; re-registering a differing definition for the same identity conflicts.
CampaignAn application namespace grouping related logical work, keyed by a validated campaign key; the platform's top-level scope for submission and inspection.
Submission RunOne immutable submission invocation of a pipeline into a campaign, identified by a run key and carrying an immutable pipeline version and a configuration reference; replaying the same run key with the same immutable facts resumes safely, while conflicting facts raise a run conflict.
Input ReferenceThe opaque transport reference that identifies the caller's work request; the platform stores it and passes it through admission but never interprets or resolves it.
Output ReferenceA non-empty immutable reference returned by a successful stage callable and recorded on the stage execution; the platform stores it as evidence but never interprets or resolves it, and a failed stage may not store one.
LabelAn application-supplied string key and value carried on one unit of work, used only for exact-match selector control; the platform never interprets what a label means.
Work InputOne validated, immutable item at the submission boundary carrying a work key, a non-empty input reference string, and a label mapping; the same values can arrive from any source transport.
Work ItemOne unit of platform-scheduled logical work, unique within a campaign by campaign key and work key; the first matching item fixes its immutable input reference and labels, and later matching submissions count it as already existing.
Stage ExecutionOne logical execution of one pipeline stage for one work item across attempts, carrying its state, current attempt, stable admission-ordering position, and optional output reference; it succeeds only when its completion transaction commits and fails when the application stage callable raises, and also fails or is cancelled when the sweep projects DBOS abandonment onto it.
Stage AttemptOne append-only attempt row in a stage execution's ordered sequence, carrying an attempt number, a DBOS workflow id, and, once terminal, a terminal summary and terminal reference; the application stage body inside one attempt may be replayed by DBOS.
Stage Execution StateThe logical state of a stage execution: one of READY, ADMITTED, SUCCEEDED, FAILED, or CANCELLED, with no RUNNING member. Platform state, not DBOS workflow status, is authoritative for it.
AdmissionThe transactional stage-entry pass in which READY work, in stable randomized order, is admitted under matching controls and paused state, with each admitted attempt's workflow enqueued on the stage's DBOS queue; one bounded pass commits as one transaction, isolating a single unhealthy stage or repeatedly-failing work item from the rest of the pass.
Admission PayloadThe package-owned, frozen record supplied to a stage's args_for at admission, containing only routing identity and immutable submission facts — campaign, work, and run keys, the input reference, labels, pipeline key and version, stage key, and attempt number; the platform never interprets the arguments args_for derives from it.
Stage ControlA persisted per-stage control keyed by pipeline key, version, and stage key together with an exact-label selector, carrying a capacity and a paused flag; the empty-selector control is required before a stage admits anything.
Selector CapacityThe maximum concurrent ADMITTED occupancy a matching stage control allows for work whose labels satisfy that control's exact-label selector; it is desired concurrent occupancy, not a worker count and not a request-rate or token limit.
Empty-Selector CapacityThe required stage-wide control, whose selector is empty, that every declared stage must have before admission; without it the stage's work is unconfigured and stays unadmitted.
PauseA flag set on an already-existing stage control that stops admission through that control without changing its capacity or interrupting running work; pausing or resuming a never-configured selector raises.
Scheduled DispatcherA per-process registration that owns its DBOS client and runs bounded admission passes on a schedule, optionally also scheduling the abandoned-stage sweep; it requires every registered pipeline to be a wrapped pipeline, and its registration must stay alive while the runtime runs.
Wrapped PipelineThe pipeline definition returned by the wrapper operation, whose stage callables are replaced with package-owned workflows that commit stage outcome and create the next READY stage atomically; only a fully wrapped definition runs the completion transaction, so the execution wiring (scheduled dispatcher registration) rejects an unwrapped declaration.
Stage HandoffThe single completion transaction in which a succeeding stage's terminal attempt, its stage execution's SUCCEEDED state, and the next linear stage as READY all commit exactly once; a running workflow not matching its persisted current ADMITTED attempt is a handoff mismatch, except that a late completion by the current attempt of a CANCELLED stage is silently discarded — operator cancellation wins, and the late completion neither rewrites terminal state nor creates the next stage.
RetryThe operation that returns a terminal FAILED stage execution to READY with exactly one new attempt for later admission; only a FAILED stage is eligible, and CANCELLED and all other states are not.
CancellationThe operation that makes a work item's current logical stage terminal (CANCELLED) before delegating cancellation of the exact admitted DBOS workflow; it is non-recursive, permanently prevents the item from being re-admitted or advanced within its campaign, and re-issues an idempotent delegation when a prior post-commit delegation was lost.
SweepThe projection that moves currently ADMITTED stages whose DBOS workflow is CANCELLED, errored, or recovery-exhausted into terminal platform state and reclaims their occupancy; it never retries, resumes, replaces, or waits, and platform state remains authoritative.
Capacity OccupancyThe count of currently ADMITTED stage executions matching a control's selector, compared against that control's capacity during admission; nothing releases occupancy for an abandoned workflow automatically, so the sweep must reclaim it.

Guarantees

Platform State Is Authoritative for Logical Outcome. The platform's own tables are the source of truth for a stage execution's state; DBOS workflow status is treated as execution evidence, never as the logical outcome.
  • Registers only immutable pipeline definitions, one per pipeline identity; re-registering a differing definition for the same identity conflicts.
  • Rejects wiring a scheduled dispatcher over a registry containing a pipeline that is not a wrapped pipeline — only a wrapped definition runs the completion transaction; a submission-only registry may hold unwrapped declarations.
  • Resumes a replayed submission run with the same immutable facts, and raises a run conflict on conflicting facts; the first matching work item fixes its input reference and labels.
  • Stores and passes through every reference — both input reference and output reference — without ever interpreting or resolving it.
  • Never admits a stage that lacks its empty-selector capacity; admission holds ADMITTED occupancy at or under each matching control's capacity.
  • Selects READY work in a stable randomized order, commits admission as one bounded pass, and isolates a single unhealthy stage or repeatedly-failing work item from the rest of the pass.
  • Stops admission through a paused control without changing its capacity or interrupting running work; pausing or resuming a never-configured selector raises.
  • Commits each stage handoff — terminal attempt, SUCCEEDED state, and the next READY stage — exactly once, and rejects a workflow that does not match its persisted current ADMITTED attempt as a handoff mismatch — except that a late completion by the current attempt of a CANCELLED stage is silently discarded, so operator cancellation wins and the late completion neither rewrites terminal state nor creates the next stage.
  • Retries only a terminal FAILED stage execution, preparing exactly one new attempt back to READY; CANCELLED and all other states are ineligible.
  • Cancellation is non-recursive, permanently prevents the item from being re-admitted or advanced within its campaign, and re-issues an idempotent delegation when a prior one was lost.
  • The sweep never retries, resumes, replaces, or waits — it only projects abandoned ADMITTED stages into terminal state and reclaims their occupancy.
  • Records an output reference only on a successful stage; a failed stage may not store one.

In vs. Out of Scope

In scopeOut of scope
  • Immutable versioned pipeline definition and registry
  • Durable streaming submission and work-item admission
  • Selector-capacity and empty-selector controls, pause, and resume
  • Admission, stage handoff, retry, cancellation, and sweep
  • Campaign, run, and stage inspection
  • Domain-neutral DBOS durability and colocation
  • Schema management and telemetry initialization
  • Interpreting application payloads
  • Resolving input or output references
  • Persisting or binding stage results
  • Non-linear pipelines or graph nodes
  • Rollout, provider, graph, or officialness semantics
  • Worker pools and request-rate or token limiting

Exported Names

Each row maps a term, or a group of supporting exports, to names in dr_platform.__all__. Every exported name appears exactly once in the names column; there are no aliases or alternate spellings. The primitives work, reference, queue, workflow, attempt, control, selector, capacity, terminal, idempotent, durability, and colocation, along with the terms input reference, output reference, label, capacity occupancy, selector capacity, and empty-selector capacity, name concepts rather than exports, so they have no row. Admission likewise has no row: it runs inside the scheduled dispatcher and reports unhealthy stages through its logs rather than raising a catchable exported error.
