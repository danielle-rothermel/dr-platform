dr-platform scope and test audit

dr-platform · 2026-07-15
The first implementation layer has removed the clearest scope violations: publication, export, projection, DuckDB, MotherDuck, Unitbench signing, OpenSSL integration, DBOS dependency self-tests, and Whetstone policy. PR 2 then replaced manifest preparation and source-mutation policing with one submission-owned read. PR 3 assigned validation to caller boundaries and PostgreSQL instead of re-auditing typed rows. PR 4 removed the remaining cycle-hiding runtime imports and internal private-module crossings. The remaining work is deliberately visible: PostgreSQL integration still spans 162 collected cases, and many tests remain coupled below the public interface.

Implementation ledger. This base audit records every action as pending. Each stacked PR must update the affected finding after implementation and verification. A mixed block remains visibly in progress until every checklist item is complete; pending work is never hidden by a partially completed finding.

Definite removal findings

F01 · DuckDB is a mandatory dependency and a public package feature

Critical · remove

This is not lockfile residue. DuckDB is installed for every consumer, imported by production modules, opened directly at runtime, and represented in result types and default destination identifiers.

The audited base declared DuckDB in pyproject.toml, implemented local export in src/dr_platform/export.py, implemented pins and cleanup in publication.py, and opened MotherDuck from platform_v6_preflight.py. PR 1 removed all four paths and their 40 root exports.

Removal boundary: delete the export/publication subsystem and its tests, remove its root exports, remove the dependency, and regenerate uv.lock. Editing the lockfile alone would leave import failures.

Implementation status · Complete in PR 1
  • Delete DuckDB runtime code and tests.
  • Remove public exports and the direct dependency.
  • Regenerate and verify the lockfile.

F02 · Application data projection is implemented inside the execution package

Critical · remove

ProjectionSpec, typed projection columns, full-rebuild builders, source snapshots, destination DDL, row normalization, checksums, remote staging, and application-specific export all live in dr_platform. This is the direct data-projection link the audit was asked to find.

The audited export.py owned projection schemas and builders, while the package root made those types first-class public API. PR 1 deleted the implementation, exports, and tests together.

Removal boundary: remove projection types, application snapshot/export paths, remote publication, and projection tests together. Do not preserve compatibility aliases if the goal is a clean break.

Implementation status · Complete in PR 1
  • Delete projection and application-export implementations.
  • Delete projection-facing public API and tests.

F03 · MotherDuck and Neon behavior is embedded in the production protocol

Critical · remove

Vendor selection changes schemas, timestamp functions, isolation levels, SQLSTATE handling, JSON types, cleanup capabilities, and retry classification. The package is therefore not a vendor-neutral execution kernel even where the public class is named “Postgres.”

The audited publication and preflight modules branched on MotherDuck and Neon behavior, hard-coded a MotherDuck endpoint and token flow, and preserved a live capability exception in CI. PR 1 deleted those paths.

Removal boundary: remove vendor preflight commands, vendor capability branches, CI/skip-budget exceptions, publication tests, and the motherduck: secret-prefix special case.

Implementation status · Complete in PR 1
  • Delete MotherDuck and Neon publication behavior.
  • Remove vendor preflight, CI, and test exceptions.
  • Remove vendor-specific secret heuristics.

F04 · Unitbench interoperability defines the signing wire format

Critical · remove

There is no Unitbench import or package dependency, but there is explicit protocol coupling: canonical JSON ordering, JavaScript-safe integers, DER/SPKI key representation, and OpenSSL signing/verification exist to match Unitbench's reader.

The audited publication module implemented the Unitbench-compatible cross-language contract, while test_signed_integrity_jcs.py pinned Node-compatible vectors and real OpenSSL behavior. PR 1 removed both.

Removal boundary: removing publication makes this entire signing stack obsolete: signer types, JCS encoder, key verification, fixture vectors, OpenSSL test material, and signed-integrity tests.

Implementation status · Complete in PR 1
  • Delete Unitbench-compatible signing and JCS code.
  • Delete OpenSSL fixtures and integration tests.

Test-suite findings

Target test policy. Keep deterministic unit tests and a small PostgreSQL integration suite for behavior that depends on real transactions, locks, constraints, migrations, or password-authenticated DSN handling. Each retained PostgreSQL test should protect a distinct public guarantee that a unit test cannot establish. Remove all DuckDB, MotherDuck, and OpenSSL integration tests; they are outside the package boundary.

F05 · PostgreSQL integration coverage is broad rather than high-leverage

High · consolidate

After PR 3, Pytest collects 275 cases and fixture analysis finds 162 requiring PostgreSQL. No cases require MotherDuck, open DuckDB, or spawn OpenSSL. PostgreSQL is a valid integration boundary, but 162 cases repeat state transitions, table shapes, and similar race variants instead of concentrating on the few guarantees that require a real database.

conftest.py now owns only PostgreSQL fixtures; ci.yml starts PostgreSQL and verifies connectivity without a vendor skip budget.

Required action: remove every DuckDB, MotherDuck, and OpenSSL integration path. Reduce PostgreSQL coverage to one focused test per database-only guarantee: fresh migration and usable schema; a representative transaction/locking race; core idempotent lifecycle persistence through a public seam; public inspection of persisted state; and credential-preserving connection behavior. Add another PostgreSQL case only when it proves a materially different database guarantee.

Implementation status · In progress
  • Remove every non-PostgreSQL integration test.
  • Consolidate PostgreSQL coverage by distinct database guarantee.
  • Verify password-preserving PostgreSQL connection behavior.

F06 · The DBOS contract suite tests the dependency's internals

High · remove

The suite imports DBOS private modules, asserts the exact installed version, exact function signatures, every private system-table column, enum membership, queue semantics, cancellation semantics, and payload deserialization behavior. This is a compatibility laboratory for DBOS 2.26, not a focused test of dr-platform's public behavior.

The removed test_dbos_226_contract.py imported five private DBOS modules and pinned exact schema/signature shapes. Production still imports private DBOS modules in dbos_config.py:17–26 and reconciliation_runtime.py:10.

Removal boundary: retain only tests for behavior the package itself wraps and promises. Delete dependency self-tests and exact private-shape assertions.

Implementation status · Complete in PR 1
  • Delete DBOS dependency self-tests.
  • Delete exact private schema, version, and signature assertions.
  • Retain only package-owned wrapper behavior.

F07 · Several tests assert source text, absence, or implementation shape

High · rewrite or remove

These tests can fail after harmless refactors while observable behavior remains correct. They inspect source strings for SQL tokens and fault-boundary names, scan the repository with regular expressions, assert removed files/symbols remain absent, pin __all__, and inspect Pydantic field dictionaries.

The removed publication recovery contract repeatedly used inspect.getsource and exact substrings; test_platform_v6_credential_hygiene.py:22–43 regex-scans all source files; test_platform_v6_enqueue_claims.py:2011–2060 enforces absent files, symbols, and source patterns; vocabulary tests pin internal model configuration and fields.

Replacement rule: keep an assertion only if it crosses a supported public seam and protects a necessary behavior. Static policy checks belong in a linter only when the policy itself is retained.

Implementation status · In progress
  • Delete source-text and repository-scan assertions.
  • Delete remaining absence and implementation-shape assertions.
  • Retain only supported public behavior checks.

F08 · “Contract” tests duplicate ordinary behavior tests

High · consolidate

The separate tests/contracts layer repeats target-registry, claim replacement, lost-outcome compensation, missing-observation rotation, cancellation, cleanup, and reconciliation behavior already covered in ordinary modules. Exact duplicate names exist, and at least eleven cross-file pairs describe the same scenario with near-identical names.

Exact duplicates include test_workflow_reference_lock_helper_sorts_and_deduplicates, test_fresh_registry_resolves_a_serialized_persisted_reference, and test_register_all_is_atomic_on_conflict. Near-duplicates cover cleanup capability, missing-candidate starvation, active-observation cancellation, claim replacement, and compensation creation.

Removal boundary: choose one public-behavior test per contract and delete the layered copy. Do not preserve “contract” as a second taxonomy unless it denotes a genuinely external interface.

Implementation status · In progress
  • Delete the obsolete layered registration/manifest contract after preserving focused public coverage.
  • Identify the surviving public-behavior test for each other duplicated contract.
  • Delete layered contract copies and the obsolete taxonomy.

F09 · Tests are coupled below the package interface

High · rewrite

The suite has 97 imports from dr_platform.* submodules versus 19 root imports, 145 mentions of monkeypatching, 368 direct references to internal schema tables, and 333 direct SQL execution calls. Seven test modules exceed 1,000 lines. Tests therefore constrain internal storage and orchestration more often than the documented five-step public flow.

PR 1 removed test_publication.py (2,227 lines), test_export.py (1,290 lines), and their obsolete contracts. The remaining largest modules include contract enqueue claims (now below its former 2,060 lines), contract registration targets (1,774), contract cancellation (1,648), contract reconciliation (1,643), and test_migrations.py (1,145).

Replacement rule: retain narrow pure tests for deterministic calculations and public contracts; delete tests made obsolete by subsystem removal; rewrite remaining behavior tests around public outputs.

Implementation status · In progress
  • Delete tests made obsolete by subsystem removal.
  • Remove unnecessary schema and private-module coupling.
  • Rewrite remaining behavior tests around public outputs.

Defensive-ceremony findings

These findings require an explicit contract decision. Some code below handles real crash and concurrency races. The finding is that the guarantee carries large ceremony—not that deleting it is automatically safe.

F10 · Publication recovery, signing, fencing, pins, and cleanup form an oversized defensive subsystem

Critical · remove with publication

publication.py is 3,584 lines and defines 23 classes, 16 top-level functions, 107 explicit raises, durable plans, signed inventories, leases, fences, pins, tombstones, cleanup eligibility, retry classification, crash hooks, and backend-specific recovery. export.py adds 2,277 more lines and 41 raises.

The audited publication module introduced a large recovery vocabulary before a 2,500-line fence class, while export duplicated local/application capture and destination paths. PR 1 deleted both modules and all 40 root names.

Decision: because publication itself is out of scope, none of its defensive guarantees need to survive in this package.

Implementation status · Complete in PR 1
  • Delete publication recovery, fencing, leases, pins, tombstones, cleanup, and signing.
  • Delete all recovery-specific tests and public types.

F11 · The same lifecycle invariants are enforced in models, SQL checks, triggers, and service code

Decision required

The source contains 31 Pydantic model validators and 103 validation functions/decorators. The baseline migration contains 77 named CHECK constraints, nine trigger functions, nine triggers, and twelve trigger-side exceptions. Many invariants—terminal timestamps, claim resolution, cancellation provenance, service priorities, and compensation shape—are repeated across all layers and then tested again directly.

records.py:304–488, 553–729 validates attempt, claim, cancellation, and compensation shapes; 0001_platform_baseline.py:233–452, 521–850 repeats them as checks and immutable-row triggers; service modules re-check state before every mutation.

Resolved ownership: public inputs and external adapter results validate at their boundaries; PostgreSQL checks, foreign keys, and triggers own durable lifecycle integrity; frozen record models decode typed rows without re-auditing the database; service checks remain only for replay, authority, CAS, and external outcomes. PR 3 added the two constraints that previously existed only in model validators before removing the repeated checks.

Implementation status · Complete in PR 3
  • Document the owner of each retained invariant.
  • Keep caller-boundary validation and critical database constraints.
  • Remove repeated internal revalidation and its implementation-shape tests.

F12 · Manifest preparation uses a layered authenticity protocol for ordinary item input

Decision required

One submission freezes format versions, target digests, per-item recipe digests, per-page digests, an all-items digest, an operation-recipe digest, and a final manifest digest. Submission then rereads and recomputes the entire chain. The JSONL adapter adds inode/device/size/mtime identity, content SHA-256, byte length, byte offsets, and before/after identity checks around reads and hashing.

manifests.py:22–125 defines versioned, self-hashing manifests; submission.py:274–351, 954–1075 computes and revalidates the digest tree; jsonl.py:68–167, 194–250, 335–352 adds filesystem drift detection.

Resolved contract: submission owns one authoritative read, validates caller input at that boundary, and persists only runtime identity and resumable-registration state. It does not defend against caller mutation between a separate preparation and submission phase because that separate phase no longer exists.

Implementation status · Complete in PR 2
  • Make submission own one authoritative source traversal.
  • Remove filesystem mutation-defense metadata and rereads.
  • Remove digest layers without a remaining runtime consumer.

F13 · Target registration makes callers assemble and cross-validate a 17-field contract

Decision required

ExecutionTarget has 17 fields, including six callables and several independently versioned concepts. Callers must separately derive a ten-field declaration and make its digest match the target reference. Recipes then repeat target identity, workflow name/version, topology, and argument-recipe version and are validated again.

targets.py:41–157 defines target identity, declaration, target construction, and cross-validation; manifests.py:29–60 repeats the recipe envelope; submission.py:1225–1246 compares the repeated fields.

Simplification direction: derive references, declarations, and digests from one target definition. Remove version fields without a demonstrated migration/compatibility consumer.

Implementation status · In progress · Future decision remains
  • Remove manifest-level copies of target identity and aggregate recipe digests.
  • Choose one authoritative target definition.
  • Remove repeated identity and unused compatibility fields.

F14 · Registration leases, page hooks, and replay checks create a second transaction protocol

Decision required

Submission uses page-level registration leases, cursor compare-and-set checks, abandonment, hook accounting, exact JSON replay comparison, nested-input mutation detection, global advisory locks, and per-workflow locks. The public submit and submit_jsonl facades each expose 13 parameters to wire this machinery.

submission.py:90–273, 354–842, 898–1259 contains the registration protocol; OperationRecord persists 39 fields, many solely for manifest, lease, cursor, and aggregate bookkeeping.

Question to resolve: does core submission need resumable multi-page registration with application hooks? If not, use one transaction or a much smaller idempotency contract and remove abandonment/lease paths.

Implementation status · In progress · Future decision remains
  • Remove nested-source mutation detection and manifest exact-replay policing.
  • Decide the required resumability and hook contract.
  • Remove protocol state outside that contract.

F15 · Enqueue uncertainty recovery persists three ledgers and a compensation state machine

Decision required

The kernel records claims before DBOS calls, separately records call start and outcome, recovers expired call-started claims through authoritative observation, replaces absent calls, creates compensations after lost authority, and records successor hazards if a workflow appears late. This is rigorous, but it is a large contract for a rare uncertainty window.

claims.py is 1,784 lines; enqueue_runtime.py:355–591 implements call-start/outcome recovery; cancellation.py is 1,517 lines and repairs late compensation; schema tables include enqueue_claims, enqueue_compensations, and enqueue_compensation_hazards.

Question to resolve: is exactly-once-ish recovery across a crash between DBOS enqueue and local outcome persistence a core promise? If not, a simpler idempotent DBOS workflow ID plus retry policy can replace much of this protocol. If yes, keep it and stop describing its checks as incidental defense.

Implementation status · Pending future decision
  • Decide whether lost-outcome recovery is a core promise.
  • Keep or remove ledgers consistently with that decision.

F16 · Missing-workflow hysteresis and cancellation cuts expand ordinary retry/cancel semantics

Decision required

Missing DBOS rows are not treated as simple absence. The package persists repeated observations and grace periods, rotates reobservation pages, tracks source-attempt provenance, compares operation cuts, locks reference hierarchies, distinguishes local/foreign cancellation, and requires explicit operator confirmation for some successor attempts.

reconciliation.py is 1,451 lines; cancellation.py:61–211 defines expected-cut and inspection vocabulary; cut.py:20–100 adds externally pinned cut comparison; the schema persists missing_reobservations and next_attempt_requests.

Question to resolve: which ambiguous/missing states have actually occurred and must be durable? Remove speculative states and their ledgers; retain only recurrence-backed recovery behavior.

Implementation status · Pending future decision
  • Identify recurrence-backed ambiguous states.
  • Remove speculative recovery states and tests.

F17 · Secret detection and telemetry safety rely on heuristic content policing

High · simplify

Workflow arguments are recursively scanned for key fragments such as token, secret, and dsn, plus vendor-specific URL prefixes. Telemetry uses a closed attribute allowlist and rejects text that resembles credentials. These checks can reject legitimate domain values, duplicate application responsibility, and still cannot prove an arbitrary payload is secret-free.

enqueue_runtime.py:65–80, 835–878 contains the recursive scanner; telemetry.py:14–29, 63–124 contains content heuristics and a Whetstone-aware closed allowlist. Tests explicitly pin Anthropic/model/cost/token examples.

Simplification direction: define a small documented metadata contract and keep opaque application payloads out of telemetry by construction. Do not infer secrets from arbitrary key names and string prefixes.

Implementation status · In progress
  • Remove vendor and downstream-specific telemetry policy.
  • Replace heuristic payload policing with a small metadata boundary.

F18 · Import cycles and private cross-module dependencies are repaired at runtime

High · remove, then simplify

Export and publication import each other's internals through lazy imports; publication imports thirteen private export symbols and later imports result models at module bottom, then calls model_rebuild to resolve the cycle. Reconciliation/runtime and cancellation have similar lazy/private crossings. This is architectural ceremony caused by responsibilities being split at unstable seams.

PR 1 removed the intentional export/publication cycle. PR 4 then removed the obsolete export-writer lock edge, moved PostgreSQL coordination and operation lifecycle aggregation to leaf modules, placed reconciliation candidates with their persistence owner, and hoisted the now-acyclic runtime imports.

Removal boundary: deleting export/publication eliminates the worst cycle. Move genuinely shared remaining concepts to leaf modules rather than preserving lazy imports.

Implementation status · Complete in PR 4
  • Remove cycles deleted with publication/export.
  • Move remaining shared lifecycle and locking concepts to leaf modules.
  • Remove runtime lazy imports that only conceal cycles.

Standalone-package findings

F19 · Whetstone and AI-generation vocabulary appears in production policy

Critical · remove

Five production telemetry keys are namespaced to whetstone.* and describe providers, models, token counts, provider cost, and throttle delay. Tests use Anthropic and Claude identifiers. The README and record documentation mention prompts, model configuration, and provider payloads. These are downstream AI/evaluation concerns, not platform vocabulary.

telemetry.py:120–124 hard-codes Whetstone fields; test_platform_v6_telemetry_hygiene.py:69–105 pins AI-specific examples; README.md:8–10 and records.py:89–103 use provider language.

Removal boundary: delete Whetstone keys and tests. Replace documentation examples with neutral execution payload language only where the concept remains necessary.

Implementation status · Complete in PR 1
  • Delete Whetstone telemetry keys and tests.
  • Replace AI/provider examples with neutral package language.

F20 · Fixed batch scheduling policy prevents neutral reuse

High · redesign

Every item must choose one of urgent, standard, or backfill; each maps to a fixed numeric priority enforced by public enums, application models, database checks, migration SQL, and tests. Queue validation also requires every DBOS queue to be database-backed and priority-enabled. This favors sweep/backfill workloads over a neutral durable-execution package.

status.py:86–100 fixes classes and priorities; items.py:20–30 requires service_class on every item; enqueue_runtime.py:281–299 rejects non-priority queues; migration checks pin the same values and numbers.

Standalone direction: accept a caller-supplied priority or make scheduling policy an optional adapter. Do not persist downstream class names as universal package vocabulary.

Implementation status · Pending future decision
  • Choose caller-owned priority or an optional scheduling adapter.
  • Remove fixed downstream classes from the core.

F21 · The package describes and shapes itself around large sweeps

High · narrow or generalize

Project metadata explicitly says “running large sweeps.” The core contract assumes operations contain ordered item sets, group keys, manifests, pages, deterministic shuffle ranks, batch aggregate counters, backfill priority, and JSONL ingestion. Those can be a valid product, but they are not neutral infrastructure for arbitrary DBOS use.

pyproject.toml:4 defines the package around sweeps; README.md:3–18 presents the operation/item/attempt pipeline; manifests, submission, JSONL, schema, and inspection all make the collection model structural.

Decision: either embrace a focused batch-execution package and stop claiming broad reuse, or remove group/page/manifest/aggregate concepts from the core. A rename in documentation alone will not generalize the API.

Implementation status · Pending future decision
  • Choose the package's durable product boundary.
  • Align metadata, API, schema, and documentation to that boundary.

F22 · The package root exposes subsystem internals instead of a standalone core

High · curate

The README describes a small flow—register, submit, reconcile/wait, inspect, cancel—but dr_platform.__all__ contains 132 names. Export/publication contribute 40; backoff contributes 14. Conversely, several protocols accepted by public functions are not root-exported, so the root is simultaneously too wide and incomplete.

__init__.py:1–294 flattens records, statuses, publication recovery models, projection schemas, local pin operations, telemetry capture, and throttle operations into one namespace.

Standalone direction: after removal, expose only the remaining core verbs, their direct input/result types, and required public protocols. Leave implementation records and storage operations private.

Implementation status · In progress
  • Remove obsolete subsystem exports.
  • Curate the remaining root API around supported public verbs and types.

Recommended removal sequence

  1. Delete the obvious out-of-scope subsystems: export/publication modules; vendor preflight and skip-budget code; publication, export, storage-preflight, preflight, and signed-integrity tests.
  2. Repair package and dependency surfaces in the same change: remove 40 root exports, DuckDB, publication telemetry attributes, Whetstone fields, MotherDuck URL heuristics, and regenerate the lockfile.
  3. Make the test boundary explicit: remove all DuckDB, MotherDuck, and OpenSSL integration cases. Preserve PostgreSQL as the sole database/service integration dependency, then consolidate the remaining cases into a small suite where each test proves a distinct migration, transaction, locking, constraint, persistence, inspection, or credential-handling guarantee.
  4. Choose the remaining product: either retain a focused batch/sweep kernel or generalize scheduling, manifests, grouping, JSONL, and target definitions. Do not attempt both through optional fields and compatibility layers.
  5. Simplify one defensive cluster at a time: manifest authenticity, registration leases/hooks, enqueue compensation, missing-workflow hysteresis, and cancellation cuts. For each, write the guarantee in one sentence; delete states, tables, checks, and tests that do not directly support it.
  6. Curate the final public API and tests: expose only the core verbs and types, then keep focused deterministic tests for those contracts. Avoid reintroducing implementation-shape and absence tests.

Useful core candidates remain. Hand-written DBOS fakes in enqueue/reconciliation runtime tests, deterministic identity/backoff calculations, target registry behavior, and small public orchestration tests can support a lean unit-first suite alongside a focused PostgreSQL integration set after the product boundary is chosen.
